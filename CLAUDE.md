# engraph

Local knowledge graph + intelligence layer for Obsidian vaults. Rust CLI + MCP server. llama.cpp inference with Metal GPU. MIT licensed.

## Architecture

Single binary with 26 modules behind a lib crate:

- `config.rs` — loads `~/.engraph/config.toml` and `vault.toml`, merges CLI args, provides `data_dir()`. Includes `intelligence: Option<bool>`, `max_chunks_per_file` + `group_by` (retrieval granularity), `[embedding_prefix]` (contextual prefix composition, off by default), `[embedding_prompt]` (`document` and `query`, which prompt template each half of an asymmetric embedding model is fed through — both default to `documented`, the model card's own format, and `legacy` on either side is nomic-embed-text's convention and the control it was measured against; `document` is a fingerprint component and changing it re-indexes, `query` costs nothing, and `query = "per_intent"` names the task from `QueryIntent` and ships off; `document_title` is what fills the document template's `title:` field. `none` is the default: the literal the model card gives for a document with no title. `breadcrumb` is design §5.4's rule, `Note Title > H1 > H2 > H3`; it holds every tracked answer at its rank, and #38 measured it against `none` with the rule's other two limbs on — below the answers the two are a draw on the six positive queries, and `breadcrumb` scores four of the eleven negatives higher, which is what decides it. It does not ship, and it is the closest call in `eval/probes.md`. `note` is the note's title alone and must not be used, because it pushes the exact-name answer out of the top 20, which is issue #2's failure with a shorter prefix. The key is a fingerprint component, so a change to it re-indexes. The breadcrumb still reaches the index through the keyword lane (#37) and the cross-encoder's input (#30), and both of those limbs are measured gains — see `eval/probes.md` (#36, #38)), `[ranking]` (`mode = "sorted" | "legacy"`, which ranking stage runs — `legacy` reproduces pre-#30 output byte for byte and is the control the change was measured against; `retrieval_width`, how many rows each content lane fetches per expanded query — default 60, which is what the lanes fetched at `top_n = 20` when the width was `top_n * 3`, and the width every table in `eval/probes.md` was measured at. It decides which chunks the cross-encoder can see; `top_n` truncates the output and nothing else (#49). The value is query-time and reaches no fingerprint, so a sweep costs no index work; `candidates`, `graph_reserve`, `temporal_reserve`, `shortlist_cap`, `tiebreak`; `answer_floor`, the score below which a candidate is not an answer — default 0.30, fit against the 17-query pool in `eval/probes.md`; `0.0` removes nothing and is the control. `per_note_cap` limits how many sections of one document appear in the results. The default is 0, which means no limit. It ships as a key so that §9.1 against #30 needs a sweep and not a code change), `[rerank]` (`document_title`, prepends the file's title to a candidate before the cross-encoder scores it — off by default, and worth two ranks on one probe under the sorted stage; `max_document_chars`, the ceiling on how much of a candidate the cross-encoder reads — **0, unlimited, by default** since #42: #25 fit a 1000-char cap on a CPU build for 12.3% of query time, and on CUDA the same cap saves 3.6% while truncating 14.8% of the corpus, including the sentences that answer probes 2 and 7. It stays settable, because #25's trade still holds on a CPU build; distinct from `models.rerank`, which only names the model), `[fts]` (what the keyword lane indexes beside the chunk body and how `bm25()` weights it — `heading_path` ships **on** at weight 1.0. It returns `## Level 4 Silence` to probe 3, an answer #36's embedding limb dropped — and #38 removed that limb, so the column's measured gain is gone and issue #41 is the probe that decides its default; `tags` ships **off**, because a tag records an attribute of a note rather than something the note discusses, so it drops probe 2's most direct answer and gives the adjacent negative a 97.06% result — see `eval/probes.md` (#37). Both flags are `fts_fingerprint` components, because the fingerprint hashes the declaration they build, so switching one rebuilds the keyword index in 0.1 s with no vault read and no model; the weights are query-time and reach no fingerprint, so a weight sweep costs nothing. `heading_path = false, tags = false` is the control and reproduces the pre-#37 binary exactly), `[models]` section for model overrides plus `n_threads` (llama.cpp threads per forward pass; unset means physical cores — see `llm::resolve_n_threads`), `chunk_min_chars`, the shortest section body that becomes a chunk of its own — a shorter section merges into the preceding chunk of the same file, keeping its heading line inside the merged body so its terms stay in the keyword index, and the merge stops at `TARGET_TOKENS`. The unit is characters because the chunker estimates `chars / 4`, so design §5.4's 30 tokens is 120. It is a chunker-digest component, so changing it re-indexes — and the digest moves at 0 too, so every store re-indexes once on the upgrade. **The default is 120**: it takes the eval corpus from 1598 chunks to 1461 and its 72 sub-60-character scaffolding rows to none, and the pool reads nothing against it — every negative holds or falls, every responsive set holds its coverage. `0` is the control and reproduces the pre-#43 chunking exactly (#43), `promote_bold_headings`, whether a bold-only line opens a section — a promoted line is one bold span and nothing else (`**Text**`, `__Text__`, or either with a single colon after the closing marker), so a table row, a list item and a `**Rank**: S • **Levels**: …` preamble are not one. It is deeper than any `#` heading and an ancestor of nothing, so the enclosing heading stays in the breadcrumb, the next promoted line ends the section, and the next `#` heading of any depth ends it too. The raw line stays at the head of the chunk body, so the keyword index reads `**Spells**` and only the breadcrumb reads the stripped `Spells`; a promoted line with no body of its own is not promoted, because a flat construct has no descendants to carry its text. Like `chunk_min_chars` it is a chunker-digest component, so changing it re-indexes. **The default is `true`**, which is the repository owner's ruling and not the measurement's reading: the rule sharpens probes 2 and 7 onto chunks that read as the answer alone, and it costs probe 3 three of its five answers to a flood of per-creature `**Spells**` rows whose mechanism is not diagnosed. `false` is the control and reproduces the pre-#44 chunking exactly (#44), `[obsidian]` section (CLI path, enabled flag), and `[agents]` section (registered AI agent names). `Config::save()` writes back to disk.
- `chunker.rs` — smart chunking with break-point scoring algorithm. Finds optimal split points considering headings, code fences, blank lines, and thematic breaks. `emit_section` decides what becomes a chunk, and a section whose body is under `chunk_min_chars` is not one: it merges into the preceding chunk of the same file, heading line included, and the merge stops at `TARGET_TOKENS` (#43). `structure_headings` decides what counts as a heading at all: every `#` heading, and — when `promote_bold` is on — every bold-only line, at a level deeper than any `#` heading so the ancestor stack treats it as flat (#44). `ChunkOptions` carries `chunk_min_chars` and `promote_bold_headings` as one value, so no path that chunks a file can take one setting and forget the other — a note written through the write pipeline at one setting and re-indexed at another is cut into two different sets of rows, and nothing downstream can tell. `split_oversized_chunks()` handles token-aware secondary splitting with overlap. Every number that decides a boundary lives in `chunker::limits` rather than inline, because `chunker_fingerprint` hashes them (#31) — changing one there is enough to make the next index rebuild, with no second place to remember
- `docid.rs` — deterministic 6-char hex IDs for files (SHA-256 of path, truncated). Shown in search results for quick reference
- `llm.rs` — ML inference via llama.cpp (Rust bindings: `llama-cpp-2`). Three traits: `EmbedModel` (embeddings; `embed_batch` takes `EmbedDoc` pairs, so the `title:` field is per document rather than per model — issue #36), `RerankModel` (cross-encoder scoring; `rerank_batch` takes the whole candidate set so an implementation can set up once), `OrchestratorModel` (query intent + expansion). Three llama.cpp implementations: `LlamaEmbed` (embeddinggemma-300M GGUF on Metal GPU), `LlamaOrchestrator` (Qwen3-0.6B for query analysis + expansion), `LlamaRerank` (Qwen3-Reranker-0.6B for relevance scoring). Global `LlamaBackend` via `OnceLock`. A `LlamaContext` cannot be a struct field (it borrows the model) but does span a whole batch: `LlamaEmbed::embed_formatted` and `LlamaRerank::rerank_batch` each build one and clear the KV cache between items. Also: `MockLlm` for testing, `HfModelUri` for model download, `FlexTokenizer` (HuggingFace tokenizers + shimmytok GGUF fallback), `PromptFormat` for model-family prompt templates (each half of the EmbeddingGemma pair selected by `EmbeddingPromptConfig`, `EmbedTask` naming the task a query prompt asks for, and `DocumentTitle` naming what fills the document half's `title:` field), `heuristic_orchestrate()` fast path, `LaneWeights` per query intent. `EmbedModel::fingerprint` and `RerankModel::fingerprint` carry model identity to `fingerprint::Fingerprints` — computed once at load, because they hash the GGUF's bytes
- `fts.rs` — FTS5 full-text search support. Re-exports `FtsResult` from store. BM25-ranked keyword search, weighted per column by `[fts]` (#37). Builds the MATCH expressions the store runs: `phrase_expr` (the whole query verbatim, what identity resolution in `context.rs` needs) and `any_term_expr` (each token quoted, joined with `OR`, what the search lane needs — quoting the whole query made it a phrase query that four of five seed probes matched nothing with, issue #22)
- `ranking.rs` — the ranking stage (issue #30). Builds the shortlist the cross-encoder is shown and then lets it **sort**, instead of fusing its score in as a fourth lane. `build_pool` takes content anchors in fused order and graph anchors in reach order against declared `Reserves` (`candidates` 30, `graph_reserve` 8, `temporal_reserve` 4), backfilling either way — a quota is a ceiling, so an unfilled reserve is handed back rather than left empty. Every `Candidate` carries its provenance (`rrf_rank`, `graph_rank`, `admitted_by`), which is what makes `PoolShape` able to answer #30's three separate questions: how many graph candidates existed, how many entered the pool, how many reached the output. `sort_by_rerank` orders by the model's probability with `Tiebreak` deciding exact ties only; `degraded_interleave` is the documented 3:1 fallback when no cross-encoder is available, and its confidence is a **position, not a probability**. `apply_answer_floor` then removes every candidate that the model scored below `[ranking] answer_floor` (issue #34). It applies to each candidate, so it both empties a response that has no answer and removes the low-scoring results below a correct one. It skips a candidate whose `rerank_score` is `None`, because a position is not a probability. An empty result set gives `NO_RELEVANT_CONTENT` on the CLI, and as a second MCP content block next to the empty array
- `fusion.rs` — Reciprocal Rank Fusion (RRF) engine. Merges semantic + FTS5 + graph + reranker results, keyed on `(file_id, chunk_seq)` so one document can contribute several sections. `cap_per_file` bounds that share; a cap of 1 is file-level grouping. Supports per-lane weighting, `--explain` output with intent + per-lane detail
- `markdown.rs` — section parser. Heading detection (ATX `#` headings with level tracking), section extraction by heading text, frontmatter splitting (YAML block between `---` fences). Powers section-level reading and editing
- `migrate.rs` — PARA migration engine. Heuristic classification of vault notes into Projects/Areas/Resources/Archive using priority-ordered rules (tasks, active status, recurring topics, people, reference, done/inactive). Preview-then-apply workflow generates markdown + JSON preview for review before moving files. Rollback support via `engraph migrate para --undo` reverses the last migration using SQLite migration log. Three MCP tools (`migrate_preview`, `migrate_apply`, `migrate_undo`) and three HTTP endpoints (`POST /api/migrate/preview`, `/apply`, `/undo`)
- `obsidian.rs` — Obsidian CLI wrapper. Process detection (checks if Obsidian is running), circuit breaker state machine (Closed/Degraded/Open) for resilient CLI delegation, async subprocess execution with timeout. Falls back gracefully when Obsidian is unavailable
- `health.rs` — vault health diagnostics. Orphan detection (notes with no incoming or outgoing wikilinks), broken link detection (wikilinks pointing to nonexistent notes), stale note detection (notes not modified within configurable threshold), tag hygiene (unused/rare tags). Returns structured health report
- `context.rs` — context engine. Seven functions: `read` (full note content + metadata), `read_section` (targeted section extraction by heading), `list` (filtered note listing with `created_by` filter), `vault_map` (structure overview), `who` (person context bundle), `project` (project context bundle), `context_topic` (rich topic context with budget trimming). Pure functions taking `ContextParams` — no model loading except `context_topic` which reuses `search_internal`
- `vecstore.rs` — sqlite-vec virtual table integration. Manages the `vec_chunks` vec0 table for vector storage and KNN search. Handles insert, delete, and search operations against the virtual table
- `tags.rs` — tag registry module. Maintains a `tag_registry` table tracking known tags with source attribution. Supports fuzzy matching for tag suggestions during note creation
- `links.rs` — link discovery module. Three match types: exact basename, fuzzy (sliding window Levenshtein, 0.92 threshold), and first-name (People folder, suggestion-only at 650bp). Overlap resolution via type priority (exact > alias > fuzzy > first-name)
- `placement.rs` — folder placement engine. Uses folder centroids (online mean of embeddings per folder) to suggest the best folder for new notes. Falls back to inbox when confidence is low. Includes placement correction detection (`detect_correction_from_frontmatter`) and frontmatter stripping for moved files
- `writer.rs` — write pipeline orchestrator. 5-step pipeline: resolve tags (fuzzy match + register new), discover links (exact + fuzzy), place in folder, atomic file write (temp + rename), and index update. Supports create, append, update_metadata, move_note, archive, unarchive, edit (section-level replace/prepend/append), rewrite (full content with frontmatter preservation), edit_frontmatter (granular set/remove/add_tag/remove_tag/add_alias/remove_alias ops), and delete (soft archive or hard permanent) operations with mtime-based conflict detection and crash recovery via temp file cleanup
- `watcher.rs` — file watcher for `engraph serve`. OS thread producer (notify-debouncer-full, 2s debounce) sends `Vec<WatchEvent>` over tokio::mpsc to async consumer task. Two-pass batch processing: mutations (index_file/remove_file/rename_file) then edge rebuild. Move detection via content hash matching. Placement correction on file moves. Centroid adjustment on file add/remove. Startup reconciliation via `run_index_shared`. `recent_writes` map coordination with MCP server to prevent double re-indexing of files written through the write pipeline
- `serve.rs` — MCP stdio server via rmcp SDK. Exposes 22 tools: 8 read (search, read, read_section, list, vault_map, who, project, context) + 10 write (create, append, update_metadata, move_note, archive, unarchive, edit, rewrite, edit_frontmatter, delete) + 1 diagnostic (health) + 3 migrate (migrate_preview, migrate_apply, migrate_undo). `edit_frontmatter` replaces `update_metadata` for granular frontmatter mutations. EngraphServer struct with Arc+Mutex wrapping for async handlers. Loads intelligence models (orchestrator + reranker) when enabled, wires into `search_with_intelligence`. Spawns file watcher on startup. CLI events table provides audit log for write operations. `recent_writes` map prevents double re-indexing of MCP-written files. HTTP mode also serves `openapi.rs` routes (`/openapi.json`, `/.well-known/ai-plugin.json`) with no auth required
- `http.rs` — axum-based HTTP REST API server, enabled via `engraph serve --http`. 23 REST endpoints mirroring all 22 MCP tools + update-metadata. API key authentication with `eg_` prefixed keys and read/write permission levels. Per-key token bucket rate limiting (configurable requests/minute). CORS with configurable allowed origins for web-based agents. `--no-auth` mode for local development (127.0.0.1 only). Graceful shutdown via `CancellationToken` coordinating MCP + HTTP + watcher exit
- `openapi.rs` — OpenAPI 3.1.0 spec builder and ChatGPT plugin manifest. Hand-written spec for all 23 HTTP endpoints, served at `GET /openapi.json`. Plugin manifest served at `GET /.well-known/ai-plugin.json`. Both routes require no authentication. `[http.plugin]` config section for name, description, contact_email, and public_url. Used by `engraph configure --setup-chatgpt` for interactive ChatGPT Actions setup
- `graph.rs` — vault graph agent. Extracts wikilinks (target *and* the `#Heading` it named, since #28) and runs the graph lane as **personalized PageRank over the chunk graph** (`PprParams`, issue #29): the seeds are the restart distribution, mass accumulates by `sum` so co-citation counts, each source chunk's mass is divided by its weighted degree so hubs cannot re-elect themselves, and a `DOC_LEVEL` link divides across the passages it could mean. Expansion follows the links of the **seed's chunk**, not its whole file — `OFF_CHUNK_LINK_WEIGHT` (0.5) is what an edge keeps when some other passage of the same file owns it. The walk returns chunks, so the lane never has to guess which section it meant, and there is no admission filter: a chunk with little mass simply sorts last
- `profile.rs` — vault profile detection. Auto-detects PARA/Folders/Flat structure, vault type (Obsidian/Logseq/Plain), wikilinks, frontmatter, tags. Content-based role detection for people/daily/archive folders by content patterns (not just names). Writes/loads `vault.toml`
- `store.rs` — SQLite persistence. Tables: `meta`, `files` (with docid, created_by), `chunks` (with vector BLOBs, `text` — the whole chunk, which the reranker scores and the keyword index reads — `snippet`, the leading 200 characters for display and *derived from `text`* by `insert_chunk` so callers pass one string rather than two, `seq`, the chunk's ordinal within its file, and the two lexical columns of #37: `heading_path`, the breadcrumb `Note Title > H1 > H2 > H3`, and `tags_text`, the file's frontmatter tags sorted and space separated. `NewChunk` is the row as it is written, one argument rather than ten), `chunks_fts` (FTS5 **external content** over `chunks`, declared over `text` and whichever of `heading_path` / `tags_text` `[fts]` enables, kept in step by three triggers. It stores an index and no text of its own, so #11's bug class — the keyword index holding a different string from the chunk — is unreachable rather than fixed, and a delete SQLite performs itself on the cascade from `files` still reaches it), `edges` (vault graph, chunk-to-chunk: `(from_file, from_chunk_seq, to_file, to_chunk_seq, edge_type)` is the unique key, with `DOC_LEVEL` = -1 for an end that names no passage — a sentinel rather than NULL because SQLite counts two NULLs as distinct in a UNIQUE constraint and `INSERT OR IGNORE` would stop deduplicating. Only the fine grain is stored; the document view is `wikilink_pairs()`, a `SELECT DISTINCT`), `tombstones`, `tag_registry`, `folder_centroids`, `placement_corrections`, `link_skiplist` (reserved), `llm_cache` (orchestrator result cache), `cli_events` (audit log for CLI operations). `chunks_vec` virtual table (sqlite-vec) for KNN search, declared at the embedding model's own width — it is not created until something establishes that width, since `Store::init` runs before any model loads. `ensure_embedding_dim()` sizes it at index time and discards the index if the width changed; `verify_embedding_dim()` guards the read and write paths. `fts_objects_sql()` builds the keyword index's declaration and its triggers from `[fts]`, and `fingerprint`'s `fts_fingerprint` hashes that text, so the enabled columns reach the fingerprint through the declaration itself; `rebuild_fts()` drops the table and its triggers, redeclares them and re-derives the index from the `chunks` table with no vault read and no model, which is the action that mismatch declares. `ensure_fts_table()` runs at init, where no config has been read, and leaves an index it did not declare alone; `sync_fts_objects()` is how a write path reconciles the declaration with `[fts]`. Enhanced `resolve_file()` with fuzzy Levenshtein matching as final fallback
- `prefix.rs` — what a chunk is embedded as, both fields. `DocContext::from_file` parses a document's identity (path, stem, frontmatter `name`, aliases, tags — the breadcrumb leads with the **path** since #46, because `name` is a cc-isekai convention engraph reads and never writes and Obsidian titles a note by its filename; `[breadcrumb_root]` selects `path` / `name` / `stem`, it is a chunker-digest component because it is stored in `chunks.heading_path`, and `name` reproduces the pre-#46 binary exactly); `embed_inputs` composes each chunk's `title:` field and its body, and is the one composition the indexer and the write pipeline share — `EmbedComposition` carries the two settings together so a caller cannot thread one and forget the other, which would write vectors into a space it does not share. The body carries the contextual prefix when `[embedding_prefix]` is on (#2); the title carries the note name or the breadcrumb (#36). Storage, snippets and the keyword index keep the raw chunk body, so the prefix cannot leak into results. `breadcrumb()` is the one composition of design §5.4's rule, and `lexical_fields` is its other limb: the same string, stored on the chunk row for the keyword index to match rather than averaged into a vector (#37). `PrefixConfig` is off by default and each component (`path`/`heading`/`tags`/`aliases`) is separately switchable — see `eval/probes.md` for why.
- `fingerprint.rs` — what built the index, so the store can tell when that changed (#31). Six `meta` keys — `parser_`, `chunker_`, `link_`, `fts_`, `embedding_`, `reranker_fingerprint` — each with one declared `Action` on mismatch: `Reindex`, `RebuildEdges`, `RebuildFts`, or `InvalidateThresholds`. Two kinds of input: *data*, hashed exactly (chunk limits, the text `store::fts_objects_sql` builds from `[fts]`, config, model and tokenizer artifact digests), and *algorithm*, carried by a hand-bumped version constant because there is no runtime view of what a function does. `CHUNK_RECORD_VERSION` sits beside `CHUNKER_VERSION` in the chunker's digest and asks the other question: not whether the chunks would fall in the same places, but whether the row written for a chunk still holds what a reader needs. `artifact_digest` hashes a model's **bytes** — a filename is not identity — and caches the result in a `<model>.sha256` sidecar keyed on `(size, mtime)`, so the steady-state cost is a `stat` rather than 640 MB of SHA-256. `verify()` is the read-path guard and it *refuses*, matching `verify_embedding_dim`; `record()` runs at the end of an index, never alongside it, so a crash cannot leave a store claiming to match code that never finished. A store with no fingerprints is adopted rather than rebuilt: protection starts at the first recorded value
- `indexer.rs` — orchestrates vault walking (via `ignore` crate for `.gitignore` support), diffing, chunking, embedding, writes to store + sqlite-vec + FTS5, vault graph edge building (wikilinks + people detection), and folder centroid computation. Exposes `index_file`, `remove_file`, `rename_file` as public per-file functions. `run_index_shared` accepts external store/embedder for watcher FullRescan. Reconciles the store's embedding width against the model before writing anything, forcing a full rebuild when it changed, then reconciles the six fingerprints (#31) and applies whatever they declare — a full rebuild, `rebuild_fts`, or `rebuild_all_edges`, which re-derives every edge from the *vault* rather than from `chunks.text` because the chunker strips frontmatter and a chunks-only rebuild would silently drop the links written there. Fingerprints are recorded last, on the way out.
- `temporal.rs` — temporal search lane. Extracts note dates from frontmatter `date:` field or `YYYY-MM-DD` filename patterns. Heuristic date parsing for natural language ("today", "yesterday", "last week", "this month", "recent", month names, ISO dates, date ranges). Smooth decay scoring for files near but outside target date range. Provides `extract_note_date()` for indexing and `score_temporal()` + `parse_date_range_heuristic()` for search
- `search.rs` — hybrid search orchestrator. `search_with_intelligence()` runs the full pipeline: orchestrate (intent + expansions, then `ensure_original` so the user's own query is searched for whatever the model returned — issue #23) → retrieval per expansion (semantic + FTS5, then the graph lane off the merged seeds) → the ranking stage in `ranking.rs`, which by default fuses the two content lanes, routes graph and temporal candidates into the shortlist by reserved quota, and lets the cross-encoder sort it (issue #30). `[ranking] mode = "legacy"` restores the pre-#30 five-lane RRF, with the cross-encoder as a fourth voter and a per-file cap on the *results*. `search_internal()` is a thin wrapper without intelligence models. Each lane keeps **two pools**: the lane's own scores feed fusion (which reads rank), while a min-max copy normalised into `[0.1, 1.0]` per (lane × expansion) feeds `merge_seeds` and the graph lane (which reads magnitude) — `1.0 - distance` and negated BM25 do not share a scale, and normalising the *fusion* pool instead measurably regressed the probes (issue #26). Lanes dedup on `(file_id, chunk_seq)` and cap each document's share (`max_chunks_per_file` under the legacy stage, `[ranking] shortlist_cap` under the sorted one, both defaulting to 3). The sorted stage caps the **shortlist** and not the results — bound what the model is shown, because it cannot rank what it never saw; do not bound what it returns, because ranking is its job. `group_by = "file"` still collapses to one result per document under both. Adaptive lane weights per query intent including temporal (1.5 weight for time-aware queries). Results display normalized confidence percentages (0-100%) instead of raw RRF scores. `--explain` prints the retrieval step as well as the fusion step: every query actually run, its FTS MATCH expression, and per-lane hit counts. `rerank_documents()` fetches each candidate's whole chunk, truncates it to `[rerank] max_document_chars` if one is set — it is 0, unlimited, by default since #42 — before prepending any title, so the title cannot be what gets cut, and logs the assembled size at DEBUG — `RUST_LOG=engraph::search=debug` is how `eval/sweep-rerank-chars.py` reads the character counts back.
- `identity.rs` — L1 extraction engine: active projects, key people, current focus, OOO, blocking. `format_identity_block()` for compact session context. `extract_l1_facts()` called after indexing.
- `onboarding.rs` — Interactive CLI UX: welcome banner, vault scan, identity prompts (dialoguer), agent mode (--detect --json, --json). `run_interactive()`, `run_detect_json()`, `run_apply_json()`.

`main.rs` is a thin clap CLI (async via `#[tokio::main]`). Subcommands: `index` (with progress bar), `search` (with `--explain`, loads intelligence models when enabled), `status` (shows intelligence state + date coverage stats), `clear`, `init` (intelligence onboarding prompt, detects Obsidian CLI + AI agents), `configure` (`--enable-intelligence`, `--disable-intelligence`, `--model`, `--obsidian-cli`, `--no-obsidian-cli`, `--agent`, `--add-api-key`, `--list-api-keys`, `--revoke-api-key`, `--setup-chatgpt`), `models`, `graph` (show/stats), `context` (read/list/vault-map/who/project/topic), `write` (create/append/update-metadata/move/edit/rewrite/edit-frontmatter/delete), `migrate` (para with `--preview`/`--apply`/`--undo` for PARA vault restructuring), `serve` (MCP stdio server with file watcher + intelligence + optional `--http`/`--port`/`--host`/`--no-auth` for HTTP REST API).

## Key patterns

- **The keyword lane reads the chunk table:** `chunks_fts` is an FTS5 **external-content** table over `chunks`, declared over `text` plus whichever of `heading_path` / `tags_text` `[fts]` enables, and kept in step by three sync triggers (#37). It stores an index and no text of its own, so #11's bug class — the keyword index holding a different string from the chunk — is unreachable rather than fixed, and the triggers are the only writer: a chunk row inserted, updated or deleted by any path updates the index, including the delete SQLite performs itself when `files` cascades. `'rebuild'` reproduces the trigger-built index's postings and BM25 scores exactly; the *bytes* differ, because an incremental write leaves one segment per batch where a rebuild writes a single merged one
- **5-lane hybrid search:** Queries run through up to five lanes — semantic (sqlite-vec KNN embeddings), keyword (FTS5 BM25), graph (wikilink expansion), cross-encoder reranking, and temporal (date-range scoring). A research orchestrator classifies query intent and sets adaptive lane weights — the graph lane is held at or below the content lanes under every intent (issue #9), a weighting set when graph expansion excluded the seed files and so could never accumulate RRF agreement. It no longer excludes them (#29), and the weights have not been revisited since. Two-pass RRF: retrieval lanes → reranker scores top 30 → 5-lane fusion. When intelligence is off, falls back to heuristic intent classification. Temporal intent detection works with both heuristic and LLM orchestrators
- **Vault graph:** `edges` table stores directional wikilink edges (one per `[[link]]`; the reverse edge exists only when the target links back) and mention edges. Built during indexing after all files are written. An edge is **owned by its source file's content**: only that file's re-index may create or destroy it, which is why the re-index path calls `delete_outgoing_edges_for_file` and only file *removal* calls `delete_edges_for_file` (both directions). Both `edges` columns CASCADE off `files(id)`, so re-indexing must not delete the row either — see `index_file` step 5. Wikilinks that resolve to no file are recorded in `unresolved_links`. People detection scans for person name/alias mentions using notes from the configured People folder
- **Graph agent:** One PPR iteration out of the seed chunks, following wikilinks in either direction — outgoing links and backlinks (`Store::incident_wikilink_edges` returns both, oriented near-end-first, in one indexed fetch for the whole frontier). `α` damps each iteration and is inert at one. The lane does not read the query at all: its old admission filter was a weaker second copy of the FTS lane, run on the *original* query while the content lanes ran every expansion. Output is capped at `max_chunks_per_file` per document and truncated to 20, both cuts on accumulated mass
- **Smart chunking:** Break-point scoring algorithm assigns scores to potential split points (headings 50-100, code fences 80, thematic breaks 60, blank lines 20). Code fence protection prevents splitting inside code blocks
- **Edge granularity:** an edge's source is the chunk whose text held the link, so `build_edges_for_file` reads the file's chunks from the store and **requires them to be inserted already**. A link the chunker never sees (frontmatter) is attributed to `DOC_LEVEL`, which is why it still takes `content`. Target side: `[[Note#Heading]]` resolves to the chunks under that heading, and a plain link — or a heading that has since been renamed — becomes `DOC_LEVEL` rather than nothing. `indexer::backfill_edges_from_chunks` re-derives the whole table from `chunks.text` with no vault read, which is how a pre-#28 store adopts the grain; `Store::needs_edge_backfill` is the flag the migration raises
- **Incremental indexing:** `diff_vault()` compares file content hashes in SQLite against disk. A changed file keeps its `files` row — and therefore its id, and therefore every backlink keyed on that id — while its chunks, vectors, FTS rows and *outgoing* edges are cleared and recomputed; `insert_file` upserts on `path`. `writer::move_note` likewise moves the row with `update_file_path` rather than replacing it. `an_incremental_edit_and_a_full_index_agree_on_the_edges_table` (`indexer.rs`) is the invariant. Content hashes are blind to everything *outside* the file, which is what `fingerprint` covers: a chunker constant, the embedding prompt, the link resolver or the FTS schema can all change with no file changing, and `run_index_inner` reconciles those before it diffs anything
- **sqlite-vec for vector search:** Vectors stored in a `vec_chunks` virtual table (vec0). KNN search via `vec_distance_cosine()`. Real deletes — no tombstone filtering needed during search
- **Write pipeline:** 5-step process for creating/modifying notes: (1) resolve tags via fuzzy matching against tag registry, (2) discover potential wikilinks via exact + fuzzy matching, (3) suggest folder placement via centroid similarity, (4) atomic file write (temp + rename for crash safety), (5) immediate index update (embed + insert into sqlite-vec + FTS5 + edges)
- **Warm sync (file watcher):** OS thread watches vault via `notify-debouncer-full` (2s debounce). Events sent over `tokio::mpsc` to async consumer. Two-pass processing: mutations then edge rebuild. Move detection via content hash matching. Placement correction learning on file moves (centroid adjustment + frontmatter stripping). Startup reconciliation catches changes since last shutdown
- **Fuzzy link matching:** Sliding window of N words over content, compared via `strsim::normalized_levenshtein` with 0.92 threshold. First-name matching for People notes (uniqueness check, 650bp confidence, suggestion-only). Overlap resolution: exact > alias > fuzzy > first-name
- **Centroid updates:** Online mean math (`adjust_folder_centroid`). Incremented on file add, decremented on file remove. Full recompute during bulk indexing
- **Docids:** Each file gets a deterministic 6-char hex ID. Displayed in search results
- **Vault profiles:** `engraph init` auto-detects vault structure and writes `vault.toml`
- **LLM orchestrator:** Single Qwen3-0.6B call classifies query intent (exact/conceptual/relationship/exploratory), generates 2-4 query expansions, and sets adaptive lane weights. Results cached in `llm_cache` SQLite table (keyed by query SHA256). Falls back to heuristic pattern matching when intelligence is off
- **Cross-encoder reranker:** Qwen3-Reranker-0.6B scores query-document relevance via Yes/No logit softmax. Runs as 4th RRF lane on top-30 candidates from pass 1. It reads each candidate's whole `chunks.text`, not the lane-dependent preview it used to get — which is why the lane is roughly half the cost of a reranked query (`eval/probes.md`, #14)
- **llama.cpp backend:** Global `LlamaBackend` singleton via `OnceLock`. `LlamaModel` is `Send+Sync`, `LlamaContext` is `!Send` (created per-call). Metal GPU auto-detected on macOS. Models download from HuggingFace on first use with progress bar. Every context sets `n_threads` + `n_threads_batch` from `resolve_n_threads`, which defaults to **physical cores** — llama.cpp's library default is a flat `GGML_DEFAULT_N_THREADS = 4` on any machine, and counting logical CPUs instead is measurably *worse* than that on an SMT box (issue #20)
- **Prompt formatting:** `PromptFormat` auto-detects model family from GGUF filename and applies asymmetric prefixes in `embed_query` (queries) and `embed_batch` (documents). The `EmbeddingGemma` pair is the one its model card documents — `<bos>task: {task} | query: …` and `<bos>title: {title | none} | text: …` — and each half is selectable, `[embedding_prompt] document` / `query`, with `legacy` restoring nomic-embed-text's `search_query:` / `search_document:` convention as the control (issue #10). The `<bos>` is in the template because `str_to_token` is called with `AddBos::Never`. The `title:` field holds whatever `[embedding_prompt] document_title` names, composed per chunk by `prefix::embed_inputs` (issue #36). Which document template built a store is hashed into `embedding_fingerprint` from `PromptFormat::template_id`, and the title selection is hashed beside it, so switching either re-indexes; the query half reaches no fingerprint. A note's content is a document, so `placement` embeds it through `embed_batch` rather than as a query

## Data directory

`~/.engraph/` — hardcoded via `Config::data_dir()`. Contains `engraph.db` (SQLite with FTS5 + sqlite-vec + edges + llm_cache), `models/` (GGUF models + tokenizers), `vault.toml` (vault profile), `config.toml` (user config with intelligence toggle + model overrides).

Single vault only. Re-indexing a different vault path triggers a confirmation prompt.

## Dependencies to be aware of

- `llama-cpp-2` (0.1) — Rust bindings to llama.cpp. GGUF model loading + inference. Metal GPU on macOS, CUDA on Linux. Compiles llama.cpp C++ via build script (requires CMake)
- `shimmytok` (0.7) — pure Rust tokenizer that reads from GGUF metadata. Fallback when tokenizer.json is unavailable (gated HuggingFace repos)
- `tokenizers` (0.22) — HuggingFace tokenizer. Kept for FlexTokenizer HuggingFace backend
- `sqlite-vec` (0.1.8-alpha.1) — SQLite extension for vector search. Provides vec0 virtual tables with KNN via `vec_distance_cosine()`
- `zerocopy` (0.7) — zero-copy serialization for vector data passed to sqlite-vec
- `strsim` (0.11) — string similarity for fuzzy tag matching and fuzzy link matching
- `time` (0.3) — date/time handling for frontmatter timestamps
- `ignore` (0.4) — vault walking with `.gitignore` support
- `rusqlite` (0.32) — bundled SQLite with FTS5 support
- `rmcp` (1.2) — MCP server SDK for stdio transport
- `axum` — HTTP framework for REST API server
- `tower-http` — CORS middleware for axum
- `tower` — middleware layer utilities
- `rand` — random API key generation
- `tokio-util` — `CancellationToken` for graceful multi-server shutdown
- `notify` (7.0) — cross-platform filesystem notification (FSEvents on macOS, inotify on Linux)
- `notify-debouncer-full` (0.4) — debouncing + best-effort inode-based rename tracking

## Testing

- Unit tests in each module (`cargo test --lib`) — 597 tests, no network required
- Integration tests (`cargo test --test integration -- --ignored`) — require GGUF model download
- Build requires CMake (for llama.cpp C++ compilation)

## CI/CD

- CI: `cargo fmt --check` + `cargo clippy -- -D warnings` + `cargo test --lib` on macOS + Ubuntu. Ubuntu step installs CMake. **Manual dispatch only in this fork** (`gh workflow run ci.yml`) — it does not run on push or PR, so those three commands are the local gate before every commit.
- Release: native builds on macOS arm64 (macos-14) + Linux x86_64 (ubuntu-latest). Triggered by `v*` tags
- Homebrew: `devwhodevs/homebrew-tap` — formula builds from source tarball. Depends on `cmake` + `rust`.
