# knapper

Local hybrid search and MCP retrieval for Obsidian-format vaults. Rust CLI + MCP server. llama.cpp inference with Metal GPU. MIT licensed.

## Architecture

Single binary with 36 modules behind a lib crate:

- `coalesce.rs` — the query-time transform that presents a document's abutting sections as one result block, after the ranking stage; `search.rs`'s `finalize_search_output` calls it, so it runs whether or not the cross-encoder ran (#39)
- `config.rs` — loads `~/.knapper/config.toml` and `vault.toml`, merges CLI args, provides `data_dir()`. Includes `intelligence: Option<bool>`, `max_chunks_per_file` + `group_by` (retrieval granularity), `[embedding_prefix]` (contextual prefix composition, off by default), `[embedding_prompt]` (`document` and `query`, which prompt template each half of an asymmetric embedding model is fed through — both default to `documented`, the model card's own format, and `legacy` on either side is nomic-embed-text's convention and the control it was measured against; `document` is a fingerprint component and changing it re-indexes, `query` costs nothing; `document_title` is what fills the document template's `title:` field. `none` is the default: the literal the model card gives for a document with no title. `breadcrumb` is design §5.4's rule, `Note Title > H1 > H2 > H3`; it holds every tracked answer at its rank, and #38 measured it against `none` with the rule's other two limbs on — below the answers the two are a draw on the six positive queries, and `breadcrumb` scores four of the eleven negatives higher, which is what decides it. It does not ship, and it is the closest call in `eval/probes.md`. `note` is the note's title alone and must not be used, because it pushes the exact-name answer out of the top 20, which is issue #2's failure with a shorter prefix. The key is a fingerprint component, so a change to it re-indexes. The breadcrumb still reaches the index through the keyword lane (#37) and the cross-encoder's input (#30), and both of those limbs are measured gains — see `eval/probes.md` (#36, #38)), `[ranking]` (`mode = "sorted" | "legacy"`, which ranking stage runs — `legacy` reproduces pre-#30 output byte for byte and is the control the change was measured against; `retrieval_width`, how many rows each content lane fetches — default 60, which is what the lanes fetched at `top_n = 20` when the width was `top_n * 3`, and the width every table in `eval/probes.md` was measured at. It decides which chunks the cross-encoder can see; `top_n` truncates the output and nothing else (#49). The value is query-time and reaches no fingerprint, so a sweep costs no index work; `candidates`, `graph_reserve`, `temporal_reserve`, `shortlist_cap`, `tiebreak`; `answer_floor`, the score below which a candidate is not an answer — default 0.30, fit against the 17-query pool in `eval/probes.md`; `0.0` removes nothing and is the control. `per_note_cap` limits how many sections of one document appear in the results. The default is 0, which means no limit. It ships as a key so that §9.1 against #30 needs a sweep and not a code change. `coalesce_adjacent` presents a document's abutting sections as one block, after the ranking stage — query-time, reaching no fingerprint. The default is on; `false` is the byte-exact per-section control (#39)), `[lane_weights]` (what each lane's rank is worth to RRF fusion — `semantic 1.0 / fts 1.0 / graph 0.8 / rerank 1.0 / temporal 0.0`, the best configuration the seventeen pool cells of #57 measured. Query-time, reaching no fingerprint, so a sweep is a config edit with no index work. Under the default ranking stage the cross-encoder sorts the shortlist, so `semantic` and `fts` are the two that decide anything; the rest are read by `mode = "legacy"` alone. `graph` stays at or below the content lanes because graph results are disjoint from theirs and can never accumulate RRF agreement — issue #9), `[rerank]` (`document_title`, prepends the file's title to a candidate before the cross-encoder scores it — off by default, and worth two ranks on one probe under the sorted stage; `max_document_chars`, the ceiling on how much of a candidate the cross-encoder reads — **0, unlimited, by default** since #42: #25 fit a 1000-char cap on a CPU build for 12.3% of query time, and on CUDA the same cap saves 3.6% while truncating 14.8% of the corpus, including the sentences that answer probes 2 and 7. It stays settable, because #25's trade still holds on a CPU build; distinct from `models.rerank`, which only names the model), `[fts]` (what the keyword lane indexes beside the chunk body and how `bm25()` weights it — `heading_path` ships **on** at weight 1.0. It returns `## Level 4 Silence` to probe 3, an answer #36's embedding limb dropped — and #38 removed that limb, so the column's measured gain is gone and issue #41 is the probe that decides its default; `tags` ships **off**, because a tag records an attribute of a note rather than something the note discusses, so it drops probe 2's most direct answer and gives the adjacent negative a 97.06% result — see `eval/probes.md` (#37). Both flags are `fts_fingerprint` components, because the fingerprint hashes the declaration they build, so switching one rebuilds the keyword index in 0.1 s with no vault read and no model; the weights are query-time and reach no fingerprint, so a weight sweep costs nothing. `heading_path = false, tags = false` is the control and reproduces the pre-#37 binary exactly), `[models]` section for model overrides plus `n_threads` (llama.cpp threads per forward pass; unset means physical cores — see `llm::resolve_n_threads`). `models.embed = "gemini:<versioned-id>"` selects the external API-backed embedder; the local `hf:`/absent form is unchanged. `[models.embed_api]` holds that backend's non-secret knobs — `dim`, `timeout_secs`, `max_retries`, `endpoint`. The key is env-only, read from `GEMINI_API_KEY`, and never written to config. `chunk_min_chars`, the shortest section body that becomes a chunk of its own — a shorter section merges into the preceding chunk of the same file, keeping its heading line inside the merged body so its terms stay in the keyword index, and the merge stops at `TARGET_TOKENS`. The unit is characters because the chunker estimates `chars / 4`, so design §5.4's 30 tokens is 120. It is a chunker-digest component, so changing it re-indexes — and the digest moves at 0 too, so every store re-indexes once on the upgrade. **The default is 120**: it takes the eval corpus from 1598 chunks to 1461 and its 72 sub-60-character scaffolding rows to none, and the pool reads nothing against it — every negative holds or falls, every responsive set holds its coverage. `0` is the control and reproduces the pre-#43 chunking exactly (#43), `promote_bold_headings`, whether a bold-only line opens a section — a promoted line is one bold span and nothing else (`**Text**`, `__Text__`, or either with a single colon after the closing marker), so a table row, a list item and a `**Rank**: S • **Levels**: …` preamble are not one. It is deeper than any `#` heading and an ancestor of nothing, so the enclosing heading stays in the breadcrumb, the next promoted line ends the section, and the next `#` heading of any depth ends it too. The raw line stays at the head of the chunk body, so the keyword index reads `**Spells**` and only the breadcrumb reads the stripped `Spells`; a promoted line with no body of its own is not promoted, because a flat construct has no descendants to carry its text. Like `chunk_min_chars` it is a chunker-digest component, so changing it re-indexes. **The default is `true`**, which is the repository owner's ruling and not the measurement's reading: the rule sharpens probes 2 and 7 onto chunks that read as the answer alone, and it costs probe 3 three of its five answers to a flood of per-creature `**Spells**` rows whose mechanism is not diagnosed. `false` is the control and reproduces the pre-#44 chunking exactly (#44), `carry_orphan_headings`, whether a bodyless `#` heading whose line no descendant breadcrumb and no promoted-line carry keeps is folded into a neighbour rather than dropped — a same-level sibling forward into the next section's text, a shallower heading or the end of the file backward onto the previous chunk's, and a file that is nothing but headings into one chunk. The line reaches `chunks.text` only, never a breadcrumb, so its terms stay in the keyword index without renaming any section. Like `chunk_min_chars` it is a chunker-digest component, so changing it re-indexes. **The default is `true`**; `false` is the control and reproduces the pre-#54 chunking exactly (#54), `[agents]` section (registered AI agent names), and `[watcher]` section (`backend` = `auto` | `native` | `poll` and `poll_interval_secs`, the warm-sync file-watch backend — `auto` polls only on a filesystem inotify cannot service, `KNAPPER_WATCHER_BACKEND` overrides, #83), and `[calibrated]` (calibrated score fusion for the model-free path, spec 2026-08-30 — `enabled`, default `true`, read only when `[ranking] mode = "sorted"` runs with no cross-encoder configured, and inert with one configured; `false` sends a no-model build to the legacy stage instead, byte for byte, the control; `semantic` 13.878, `keyword` 13.571 and `intercept` -5.848, the pin-fit logistic's three coefficients — 33 tier-1 positives against 1228 labeled negatives, leave-one-query-out validated, provenance `eval/calibrated-fusion-report-2026-08-30.txt` via the refit tool `eval/calibrated-fusion-eval.py`; `floor` 0.75, the probability below which a candidate is not an answer, `[ranking] answer_floor`'s analog for this path — `0.0` removes nothing and is the floor's own control. All five keys are query-time and reach no fingerprint, so a sweep is a config edit with no index work). `Config::save()` writes back to disk.
- `chunker.rs` — structure-first chunking: a file's sections become chunks, packed to `TARGET_TOKENS`. `smart_chunk`'s break-point scoring — headings, code fences, blank lines, thematic breaks — still exists but sits off the live path (see below). `emit_section` decides what becomes a chunk, and a section whose body is under `chunk_min_chars` is not one: it merges into the preceding chunk of the same file, heading line included, and the merge stops at `TARGET_TOKENS` (#43). The minimum reaches a section's *pieces* too: a short leading piece that a split would otherwise flush as a stub row of its own is folded forward into the following paragraph, and the combination is emitted whole, so the heading leads real section content — never backward, since a first piece's preceding chunk is a different section (#51). `structure_headings` decides what counts as a heading at all: every `#` heading, and — when `promote_bold` is on — every bold-only line, at a level deeper than any `#` heading so the ancestor stack treats it as flat (#44). `structure_headings` is `markdown::headings_with_promotions` with the bodyless promotions dropped: a promoted line with no body of its own starts no chunk, because a flat construct has no descendants to carry its text, and it is still a section `read --section` and `update --section` address (#44, #69). A `#` heading whose own body is empty is not a chunk: when its next heading is strictly deeper it survives in that descendant's `heading_path`, and when `carry_orphan_headings` is on and no such descendant keeps it — a same-level sibling, a shallower heading, or the end of the file — its line is carried instead of lost, forward into the next section's text for a sibling and backward onto the previous chunk's for a shallower one or the file's end, with a headings-only file kept as one chunk (#54). A promoted line is an ancestor of nothing, so a heading emptied by promotion is carried forward into that promoted section's text (#44). `ChunkOptions` carries `chunk_min_chars`, `promote_bold_headings` and `carry_orphan_headings` as one value, so no path that chunks a file can take one setting and forget the other — a note written through the write pipeline at one setting and re-indexed at another is cut into two different sets of rows, and nothing downstream can tell. `structure_chunk` packs whole paragraphs to `TARGET_TOKENS` and emits a single over-budget paragraph or table whole rather than tearing it; `split_oversized_chunks()` is the sole place a block is torn, and it tears only above the embed model's real input wall (`EmbedModel::max_context`), on sentence boundaries with `OVERLAP_TOKENS` of overlap, rather than at a fixed size (#75). Every number that decides a boundary lives in `chunker::limits` rather than inline, because `chunker_fingerprint` hashes them (#31) — changing one there is enough to make the next index rebuild, with no second place to remember
- `docid.rs` — deterministic 6-char hex IDs for files (SHA-256 of path, truncated). Shown in search results for quick reference
- `llm.rs` — ML inference via llama.cpp (Rust bindings: `llama-cpp-2`). Two traits: `EmbedModel` (embeddings; `embed_batch` takes `EmbedDoc` pairs, so the `title:` field is per document rather than per model — issue #36; `dim` and `token_count` size vectors and budget chunks, and `max_context()` reports the model's real-token input wall, read from the GGUF at load (`n_ctx_train`), falling back to `FALLBACK_MAX_CONTEXT` when the model reports none — it is the ceiling `split_oversized_chunks` enforces, issue #75) and `RerankModel` (cross-encoder scoring; `rerank_batch` takes the whole candidate set so an implementation can set up once). Two llama.cpp implementations: `LlamaEmbed` (embeddinggemma-300M GGUF on Metal GPU) and `LlamaRerank` (Qwen3-Reranker-0.6B for relevance scoring). Nothing generates text — the orchestrator that did is gone (#59). Global `LlamaBackend` via `OnceLock`. A `LlamaContext` cannot be a struct field (it borrows the model) but does span a whole batch: `LlamaEmbed::embed_formatted` and `LlamaRerank::rerank_batch` each build one and clear the KV cache between items. Also: `MockLlm` for testing, `HfModelUri` for model download, `FlexTokenizer` (HuggingFace tokenizers + shimmytok GGUF fallback), `PromptFormat` for model-family prompt templates (each half of the EmbeddingGemma pair selected by `EmbeddingPromptConfig`, `EmbedTask` naming the task a query prompt asks for, and `DocumentTitle` naming what fills the document half's `title:` field). `EmbedModel::fingerprint` and `RerankModel::fingerprint` carry model identity to `fingerprint::Fingerprints` — computed once at load, because they hash the GGUF's bytes
- `embed_api.rs` — the optional API-backed embedder (#84). `ApiEmbedder<P: EmbedProvider>` implements `EmbedModel` and owns the `ureq` client, batch splitting at the provider's cap, bounded retry with backoff on 429/5xx/transport errors, and L2 normalization of every returned vector. `EmbedProvider` is the small per-provider surface (env var, endpoint, auth header, native dim, input-token ceiling, batch cap, identity, request builders, response parse). `struct Gemini` is the first provider (`gemini-embedding-2`), selected by `models.embed = "gemini:<versioned-id>"` with the key in `GEMINI_API_KEY`. The trait stays synchronous; the call blocks through `ureq` the way local inference does. `llm::load_embedder` routes `models.embed` by scheme and is the one construction path for both backends.
- `fts.rs` — FTS5 full-text search support. Re-exports `FtsResult` from store. BM25-ranked keyword search, weighted per column by `[fts]` (#37). Builds the MATCH expressions the store runs: `phrase_expr` (the whole query verbatim) and `any_term_expr` (each token quoted, joined with `OR`, what the search lane needs — quoting the whole query made it a phrase query that four of five seed probes matched nothing with, issue #22)
- `ranking.rs` — the ranking stage (issue #30). Builds the shortlist the cross-encoder is shown and then lets it **sort**, instead of fusing its score in as a fourth lane. `build_pool` takes content anchors in fused order and graph anchors in reach order against declared `Reserves` (`candidates` 30, `graph_reserve` 8, `temporal_reserve` 4), backfilling either way — a quota is a ceiling, so an unfilled reserve is handed back rather than left empty. Every `Candidate` carries its provenance (`rrf_rank`, `graph_rank`, `admitted_by`), which is what makes `PoolShape` able to answer #30's three separate questions: how many graph candidates existed, how many entered the pool, how many reached the output. `sort_by_rerank` orders by whichever probability filled `rerank_score` — the cross-encoder's or the calibrated logistic's — with `Tiebreak` deciding exact ties only; `degraded_interleave` is the documented 3:1 fallback for a *configured* cross-encoder failing at call time, and its confidence is a **position, not a probability** — it is not what runs for a build with no cross-encoder configured, which the calibrated logistic sorts instead (spec 2026-08-30). `into_fused` names whichever lane sorted the pool, `"rerank"` or `"calibrated"`, so `--explain` credits the right one instead of calling every sort score a rerank score. `apply_answer_floor` then removes every candidate whose sort-lane probability scored below its own floor — `[ranking] answer_floor` for the cross-encoder, `[calibrated] floor` for the logistic (issue #34). It applies to each candidate, so it both empties a response that has no answer and removes the low-scoring results below a correct one. It skips a candidate whose `rerank_score` is `None`, because a position is not a probability. An empty result set gives `NO_RELEVANT_CONTENT` on the CLI, and as a second MCP content block next to the empty array
- `calibrate.rs` — the calibrated-fusion arithmetic (spec 2026-08-30): FTS5's own `idf`, clamped the way FTS5 clamps it; the query's BM25 upper bound, `(k1 + 1) · Σ idf` with `k1 = 1.2` (FTS5's own constant) — the `[fts]` column weights do not enter it, because each term's contribution saturates at `idf · (k1 + 1)` and FTS5 folds a weight into the frequency before that ratio, so a heavier weight moves a row's score toward the same ceiling instead of raising it, and this is also the formula `eval/calibrated-fusion-eval.py` fits the shipped coefficients with; `normalize_bm25`, the `[0, 1]` fraction of that bound a candidate's raw BM25 reached, clamped rather than inverted outside it; and `probability`, the three-coefficient logistic `σ(w_s·cos + w_k·bm25n + b)` over `[calibrated]`'s weights. Pure math — no store, no model, no I/O — so `search.rs`'s `apply_calibrated_scores` is the only caller and every formula is testable against hand-computed values
- `fusion.rs` — Reciprocal Rank Fusion (RRF) engine. Merges semantic + FTS5 + graph + reranker results, keyed on `(file_id, chunk_seq)` so one document can contribute several sections. `cap_per_file` bounds that share; a cap of 1 is file-level grouping. Supports per-lane weighting from `[lane_weights]`, `--explain` output with per-lane detail
- `markdown.rs` — what a file's headings are, and which one a caller named. `parse_headings` reads the ATX headings; `headings_with_promotions` adds every bold-only line at `PROMOTED_LEVEL`, which is the set `find_section` addresses and `list --detailed` enumerates, so a caller can name the section the outline printed (#69). `find_section` takes a heading's own text — the first of that name at any depth — or its full path from its own root joined with `>`, and it runs both lookups over the ATX headings before the merged set, so an ATX heading keeps precedence over a promoted one of the same name and a partial path resolves nothing. A segment is compared through `bold_heading_text`, so `**Spells**` and `Spells` name one section. `split_frontmatter` splits the YAML block between `---` fences. Powers section-level reading and editing
- `migrate.rs` — PARA migration engine. Heuristic classification of vault notes into Projects/Areas/Resources/Archive using priority-ordered rules (tasks, active status, recurring topics, people, reference, done/inactive). Preview-then-apply workflow generates markdown + JSON preview for review before moving files. Rollback support via `knapper migrate --mode undo` reverses the last migration using SQLite migration log. PARA is the only strategy, so the capability is one word on every surface: the CLI command `migrate`, the MCP tool `migrate` and `POST /api/migrate`, each taking `mode` = preview, apply or undo (#62)
- `health.rs` — vault health diagnostics. Orphan detection (notes with no incoming or outgoing wikilinks), broken link detection (wikilinks pointing to nonexistent notes), stale note detection (notes not modified within configurable threshold), tag issues (a note under a Work folder that carries no `work` tag). Returns structured health report
- `context.rs` — context engine. Three functions: `context_read` (two modes, #80: the default returns a `NoteContent` — the whole note's body with the frontmatter stripped, or one section's markdown with its heading line included, #81 — and `metadata` returns a `NoteMetadata` instead, the note's frontmatter, links and size, which describes the whole note and so rejects a section. The two are one `ReadResult`, serialized untagged. A section is a parameter of the capability, not a capability of its own, #62), `context_list` (every note a scope admits, in path order — the store's `ORDER BY f.path`, so a folder's notes arrive together and a subtree reads as one block. An absent limit is no limit, because a caller that wants less names a scope or a limit and one cap on one surface would make the field mean two things; `0` answers none. `detailed` adds each note's headings, ATX and promoted bold lines alike, a promoted one carrying no `level`, read from the file with the frontmatter stripped and the line numbers 1-based, because the index cannot answer the outline: a short section merges into the chunk before it, an empty heading emits no chunk, and a promoted bold line sits in `chunks.heading` beside real headings. A file the store holds and the disk does not is listed with an empty outline and no error, #68), and `vault_map` (structure overview). Pure functions taking `ContextParams` — no model loading. Composite bundles over these primitives are #71's vault-defined commands (#73)
- `vecstore.rs` — sqlite-vec virtual table integration. Manages the `vec_chunks` vec0 table for vector storage and KNN search. Handles insert, delete, and search operations against the virtual table. `search_vec` takes an optional tag scope and adds `AND rowid IN (SELECT vector_id FROM chunks WHERE file_id IN rarray(?3))` to the KNN, which vec0 reads as a pre-filter rather than as a cut over an already-chosen neighbourhood, so `k` still means k in-scope rows (#60)
- `tags.rs` — the tag rule. `extract` reads a note's tags from the two sources Obsidian defines, the `tags` property and the `#tags` in the body, which are peers: neither requires the other. A `Tag` carries both spellings — `path` is folded and is the identity, `display` is what the vault wrote — and the path's first segment is its **axis**. Only the path a note carries is returned: `type/undead` does not imply a `type` tag, and a query reads the ancestors out of the path text. The five rejections in the body are an ATX heading, a code fence or span, a URL fragment, a heading inside a wikilink, and an escaped `\#`; three of them fall out of one test, that a tag opens a line or follows whitespace. `resolve_tag` is the write path's fuzzy matcher, reading `SELECT display FROM tags` and comparing one segment against the segments that share a parent, so `type/undead` and `type/undeed` score against each other and `type/undead` and `habitat/undead` do not. `TagTerm` (`Exact`/`Subtree`) is the read-side tag term grammar: `parse_term` reads one leading `#`, a trailing `/` or `/*` as the subtree marker, and folds case; `predicate` compiles one term to one SQL predicate over a `tags` row aliased `t`, a range for `Subtree` so the unique index on `path` serves it, never a `LIKE`. `ScopeTerm` is a tag or a directory (`FolderTerm`, `Exact`/`Subtree` of a vault-root path): `parse_scope_term` routes on a leading `/`, and a directory term keeps its case — because `files.path` keeps its — while a tag term folds; `folder_sql` compiles a directory term to a range predicate over `files.path` aliased `f`, the directory's own never-`LIKE` rule (#65). `Scope { all, any, none }` is the note-query side, built by `parse`, which errors naming the field when a field holds input and none of it survives parsing; `merge_scope_alias` folds the CLI's and MCP's `scope` alias into `all`. `check_terms` rejects an `all`/`any` term the vault holds no match for, naming the nearest tag from `resolve_tag` or the subtree of the term itself when that is what would have matched, and the nearest folder for an unknown directory (#65)
- `links.rs` — link discovery module. Three match types: exact basename, fuzzy (sliding window Levenshtein, 0.92 threshold), and first-name (People folder, suggestion-only at 650bp). Overlap resolution via type priority (exact > alias > fuzzy > first-name)
- `placement.rs` — folder placement engine. Uses folder centroids (online mean of embeddings per folder) to suggest the best folder for new notes. Falls back to inbox when confidence is low. Includes placement correction detection (`detect_correction_from_frontmatter`) and frontmatter stripping for moved files
- `writer.rs` — write pipeline orchestrator. 5-step pipeline: resolve tags (fuzzy match against the tag store), discover links (exact + fuzzy), place in folder, atomic file write (temp + rename), and index update, which is also where a file's tag rows are reconciled (#60). The surfaces reach five operations: `create_note`, `update_note`, `move_note`, `archive_note` (with `unarchive_note` behind `archive --undo`) and `delete_note` (soft archive or hard permanent). `update_note` takes one list of edits, which is the whole edit grammar: each edit names a section, a frontmatter property or neither (the body), and carries a mode of replace/prepend/append/remove. `apply_note_edits` applies the whole list to the text, so a batch is one file write, one mtime-based conflict check and one re-index (#62). Crash recovery is via temp file cleanup
- `watcher.rs` — file watcher for `knapper serve`. OS thread producer (notify-debouncer-full, 2s debounce) sends `Vec<WatchEvent>` over tokio::mpsc to async consumer task. The producer selects its backend from `[watcher].backend` (`KNAPPER_WATCHER_BACKEND` overrides): `native` is the `RecommendedWatcher` (inotify/FSEvents), `poll` is a `PollWatcher` at `poll_interval_secs`, and `auto` (default) `statfs`-probes the vault and polls only on a filesystem inotify cannot service — overlay, fuse, 9p, nfs, cifs — which is the Docker bind-mount case where native events never arrive (#83). Both backends drive one generic `drive_producer` loop. Two-pass batch processing: mutations (index_file/remove_file/rename_file) then edge rebuild. Move detection via content hash matching. Placement correction on file moves. Centroid adjustment on file add/remove. Startup reconciliation via `run_index_shared`. `recent_writes` map coordination with MCP server to prevent double re-indexing of files written through the write pipeline
- `serve.rs` — MCP stdio server via rmcp SDK. Exposes 18 tools, one per capability and named the way `surface::CAPABILITIES` names it, with `-` written as `_`: 5 read (search, read, list, tags, vault_map) + 5 write (create, update, delete, move, archive) + 6 index and diagnostic (index, reindex_file, status, health, validate, identity) + 1 setup (init) + 1 migrate (migrate). `list` filters by scope operators (`all`/`any`/`none`, `scope` an alias of `all`, tag or directory terms alike) through `tags::Scope`, answers in path order, and carries each note's heading outline when `detailed` is set; `tags` reports the vocabulary, whole or under one term, through `Store::tags_under` — the call an agent makes before it can filter with `list`. The tool is the CLI's `tags` command and the HTTP `GET /api/tags`, one capability spelled per surface (#61, #62). The `search` tool takes the same four operators as its scope, as optional string arrays, and hands them to the pipeline as `SearchConfig::scope` (#60). An unknown directory term answers the same repair as an unknown tag, naming the nearest folder (#65). KnapperServer struct with Arc+Mutex wrapping for async handlers. Loads the cross-encoder when intelligence is enabled, wires it into `search_with_intelligence`. Spawns file watcher on startup. CLI events table provides audit log for write operations. `recent_writes` map prevents double re-indexing of MCP-written files. HTTP mode also serves `openapi.rs` routes (`/openapi.json`, `/.well-known/ai-plugin.json`) with no auth required
- `http.rs` — axum-based HTTP REST API server, enabled via `knapper serve --http`. 19 REST endpoints under `/api` — one per capability, plus the `/api/health-check` liveness probe — declared by `routes()` and checked against `surface::CAPABILITIES` by a parity test, plus `/openapi.json` and `/.well-known/ai-plugin.json`. `/api/list` takes the scope operators the CLI and MCP take (`scope`/`all`, `any`, `none`, tag or directory terms alike, each one comma-separated string because `serde_urlencoded` reads no sequence), and `/api/tags?under=` is the vocabulary beside it (#61). `/api/list` also takes `detailed=true`, whose value is required because `serde_urlencoded` reads no bare flag. `POST /api/search` takes the same four operators as its scope, as arrays in its JSON body rather than as comma-separated strings, and an unknown tag or directory term answers 400 rather than 500, because it is the caller's own text that named nothing (#60, #65). API key authentication with `kn_` prefixed keys and read/write permission levels — a key generated before the rename keeps validating under its old `eg_` prefix. Per-key token bucket rate limiting (configurable requests/minute). CORS with configurable allowed origins for web-based agents. `--no-auth` mode for local development (127.0.0.1 only). Graceful shutdown via `CancellationToken` coordinating MCP + HTTP + watcher exit
- `openapi.rs` — OpenAPI 3.1.0 spec builder and ChatGPT plugin manifest. Hand-written spec for all 19 HTTP endpoints, built over `http::routes()` so a route with no spec entry fails a test, served at `GET /openapi.json`. Plugin manifest served at `GET /.well-known/ai-plugin.json`. Both routes require no authentication. `[http.plugin]` config section for name, description, contact_email, and public_url. Used by `knapper configure --setup-chatgpt` for interactive ChatGPT Actions setup
- `graph.rs` — vault graph agent. Extracts wikilinks (target *and* the `#Heading` it named, since #28) and runs the graph lane as **personalized PageRank over the chunk graph** (`PprParams`, issue #29): the seeds are the restart distribution, mass accumulates by `sum` so co-citation counts, each source chunk's mass is divided by its weighted degree so hubs cannot re-elect themselves, and a `DOC_LEVEL` link divides across the passages it could mean. Expansion follows the links of the **seed's chunk**, not its whole file — `OFF_CHUNK_LINK_WEIGHT` (0.5) is what an edge keeps when some other passage of the same file owns it. The walk returns chunks, so the lane never has to guess which section it meant, and there is no admission filter: a chunk with little mass simply sorts last. `graph_expand` takes an optional tag scope and drops out-of-scope candidates after the mass sort and before `cap_per_file` and the `max_expansions` truncate, so a candidate that cannot be an answer does not spend a quota slot; the walk itself is untouched, so mass still flows through an untagged note to reach an in-scope one (#60)
- `profile.rs` — vault profile detection. Auto-detects PARA/Folders/Flat structure, vault type (Obsidian/Logseq/Plain), wikilinks, frontmatter, tags. Content-based role detection for people/daily/archive folders by content patterns (not just names). Writes/loads `vault.toml`
- `store.rs` — SQLite persistence. Tables: `meta`, `files` (with docid, created_by), `chunks` (with vector BLOBs, `text` — the whole chunk, which the reranker scores and the keyword index reads — `snippet`, the leading 200 characters for display and *derived from `text`* by `insert_chunk` so callers pass one string rather than two, `seq`, the chunk's ordinal within its file, and the two lexical columns of #37: `heading_path`, the breadcrumb `Note Title > H1 > H2 > H3`, and `tags_text`, the file's frontmatter tags sorted and space separated. `NewChunk` is the row as it is written, one argument rather than ten), `chunks_fts` (FTS5 **external content** over `chunks`, declared over `text` and whichever of `heading_path` / `tags_text` `[fts]` enables, kept in step by three triggers. It stores an index and no text of its own, so #11's bug class — the keyword index holding a different string from the chunk — is unreachable rather than fixed, and a delete SQLite performs itself on the cascade from `files` still reaches it), `edges` (vault graph, chunk-to-chunk: `(from_file, from_chunk_seq, to_file, to_chunk_seq, edge_type)` is the unique key, with `DOC_LEVEL` = -1 for an end that names no passage — a sentinel rather than NULL because SQLite counts two NULLs as distinct in a UNIQUE constraint and `INSERT OR IGNORE` would stop deduplicating. Only the fine grain is stored; the document view is `wikilink_pairs()`, a `SELECT DISTINCT`), `tombstones`, `tags` + `file_tags` (a tag is an attribute of a note, so the junction is the fact and every count over it is derived: usage is `COUNT(*)`, and last use is `MAX(files.mtime)` over the tag's files, which is when the vault last wrote it. `tags.path` is folded and unique, so `Type/Undead` and `type/undead` are one row and one axis value, and the first spelling indexed supplies `display`. The schema stores no `parent_id` and no `depth` — a leaf row has no parent to orphan, so deletion has one rule and no recursion. `reconcile_file_tags` owns one file's rows the way `index_file` owns its chunks: read the ids the file holds, replace them, then delete each released id that no other file holds. The store folds the path it is given, so the identity column is folded whatever a caller passes), `folder_centroids`, `placement_corrections`, `cli_events` (audit log for CLI operations). `list_files` takes a `tags::Scope` — every `all` term, at least one `any` term, none of the `none` terms — ANDed with `created_by`, and answers `ORDER BY f.path`, which the UNIQUE index on `files.path` serves with no sort step. Its `limit` is an `Option`: absent emits no `LIMIT` clause; a caller's directory filter is a scope term, a case-sensitive range and never a `LIKE` (#65, #68); `tags_under` answers the vocabulary, whole or under one term folded to its subtree reading, as `TagCount { path, display, note_count }` ordered by path; `files_in_scope` answers the file ids the same `Scope` admits, and the private `scope_clauses` builds those clauses for both — a junction `EXISTS` for a tag term, a `files.path` range for a directory term — so a scope and a listing cannot drift apart (#60, #65). Both constructors — `Store::open` and `Store::open_memory` — register rusqlite's `rarray` module, which is how a resolved scope binds to a lane query as one pointer rather than one parameter per id. `chunks_vec` virtual table (sqlite-vec) for KNN search, declared at the embedding model's own width — it is not created until something establishes that width, since `Store::init` runs before any model loads. `ensure_embedding_dim()` sizes it at index time and discards the index if the width changed; `verify_embedding_dim()` guards the read and write paths. `fts_objects_sql()` builds the keyword index's declaration and its triggers from `[fts]`, and `fingerprint`'s `fts_fingerprint` hashes that text, so the enabled columns reach the fingerprint through the declaration itself; `rebuild_fts()` drops the table and its triggers, redeclares them and re-derives the index from the `chunks` table with no vault read and no model, which is the action that mismatch declares. `ensure_fts_table()` runs at init, where no config has been read, and leaves an index it did not declare alone; `sync_fts_objects()` is how a write path reconciles the declaration with `[fts]`. Enhanced `resolve_file()` with fuzzy Levenshtein matching as final fallback
- `prefix.rs` — what a chunk is embedded as, both fields. `DocContext::from_file` parses a document's identity (path, stem, frontmatter `name`, aliases, tags — the breadcrumb leads with the **path** since #46, because `name` is a cc-isekai convention knapper reads and never writes and Obsidian titles a note by its filename; `[breadcrumb_root]` selects `path` / `name` / `stem`, it is a chunker-digest component because it is stored in `chunks.heading_path`, and `name` reproduces the pre-#46 binary exactly); `embed_inputs` composes each chunk's `title:` field and its body, and is the one composition the indexer and the write pipeline share — `EmbedComposition` carries the two settings together so a caller cannot thread one and forget the other, which would write vectors into a space it does not share. The body carries the contextual prefix when `[embedding_prefix]` is on (#2); the title carries the note name or the breadcrumb (#36). Storage, snippets and the keyword index keep the raw chunk body, so the prefix cannot leak into results. `breadcrumb()` is the one composition of design §5.4's rule, and `lexical_fields` is its other limb: the same string, stored on the chunk row for the keyword index to match rather than averaged into a vector (#37). `PrefixConfig` is off by default and each component (`path`/`heading`/`tags`/`aliases`) is separately switchable — see `eval/probes.md` for why.
- `fingerprint.rs` — what built the index, so the store can tell when that changed (#31). Six `meta` keys — `parser_`, `chunker_`, `link_`, `fts_`, `embedding_`, `reranker_fingerprint` — each with one declared `Action` on mismatch: `Reindex`, `RebuildEdges`, `RebuildFts`, or `InvalidateThresholds`. Two kinds of input: *data*, hashed exactly (chunk limits, the text `store::fts_objects_sql` builds from `[fts]`, config, model and tokenizer artifact digests), and *algorithm*, carried by a hand-bumped version constant because there is no runtime view of what a function does. `CHUNK_RECORD_VERSION` sits beside `CHUNKER_VERSION` in the chunker's digest and asks the other question: not whether the chunks would fall in the same places, but whether the row written for a chunk still holds what a reader needs. `artifact_digest` hashes a model's **bytes** — a filename is not identity — and caches the result in a `<model>.sha256` sidecar keyed on `(size, mtime)`, so the steady-state cost is a `stat` rather than 640 MB of SHA-256. `verify()` is the read-path guard and it *refuses*, matching `verify_embedding_dim`; `record()` runs at the end of an index, never alongside it, so a crash cannot leave a store claiming to match code that never finished. A store with no fingerprints is adopted rather than rebuilt: protection starts at the first recorded value
- `indexer.rs` — orchestrates vault walking (via `ignore` crate for `.gitignore` support), diffing, chunking, embedding, writes to store + sqlite-vec + FTS5, vault graph edge building (wikilinks), and folder centroid computation. Exposes `index_file`, `remove_file`, `rename_file` as public per-file functions. `run_index_shared` accepts external store/embedder for watcher FullRescan. Reconciles the store's embedding width against the model before writing anything, forcing a full rebuild when it changed, then reconciles the six fingerprints (#31) and applies whatever they declare — a full rebuild, `rebuild_fts`, or `rebuild_all_edges`, which re-derives every edge from the *vault* rather than from `chunks.text` because the chunker strips frontmatter and a chunks-only rebuild would silently drop the links written there. Fingerprints are recorded last, on the way out. `index_file` reconciles the file's tag rows from `tags::extract` as its last step, and `remove_file` reads the ids the file releases before the cascade and prunes them after it. The write pipeline calls the same reconciler at the six places it used to author `files.tags`, so the vocabulary has one author.
- `temporal.rs` — temporal search lane. Extracts note dates from frontmatter `date:` field or `YYYY-MM-DD` filename patterns. Heuristic date parsing for natural language ("today", "yesterday", "last week", "this month", "recent", month names, ISO dates, date ranges). Smooth decay scoring for files near but outside target date range. Provides `extract_note_date()` for indexing and `score_temporal()` + `parse_date_range_heuristic()` for search
- `search.rs` — hybrid search orchestrator. `search_with_intelligence()` runs the full pipeline: retrieval for the user's query and no other (semantic + FTS5, then the graph lane off the merged seeds) → the ranking stage in `ranking.rs`, which by default fuses the two content lanes, routes graph and temporal candidates into the shortlist by reserved quota, and lets the cross-encoder sort it (issue #30). With no cross-encoder configured the sorted stage still runs and a calibrated logistic sorts the pool instead: each content lane's score normalizes onto one absolute `[0, 1]` scale and `apply_calibrated_scores` fuses the pair with three fitted coefficients into the same `rerank_score` slot the cross-encoder writes, so the sort, the floor and the confidence all read one field (spec 2026-08-30). `[calibrated] enabled = false` routes a no-model build to the legacy stage instead, byte for byte — the control. `[ranking] mode = "legacy"` restores the pre-#30 five-lane RRF, with the cross-encoder as a fourth voter and a per-file cap on the *results*. Both stages converge on `finalize_search_output`, which applies `coalesce::coalesce_adjacent` there, so the merge runs whether or not the cross-encoder ran (#39). `SearchConfig::scope` is the `Scope` a query runs under — tag terms, directory terms, or a mix in the same `all`/`any`/`none` — empty by default: `search_with_intelligence` resolves it once through `Store::files_in_scope` **before it embeds anything**, hands the ids to all three retrieval lanes and to `temporal_seeds`, and short-circuits to an empty result — no model call, no lane — when the scope admits no note. Resolving first is what separates the two failures a scope has: a term naming no tag or directory at all errors out of `files_in_scope` with the nearest one, while a scope no note satisfies is answered honestly and empty (#60, #65). Each lane keeps **two pools**: the lane's own scores feed fusion (which reads rank), while a min-max copy normalised into `[0.1, 1.0]` per lane feeds `merge_seeds` and the graph lane (which reads magnitude) — `1.0 - distance` and negated BM25 do not share a scale, and normalising the *fusion* pool instead measurably regressed the probes (issue #26). Lanes dedup on `(file_id, chunk_seq)` and cap each document's share (`max_chunks_per_file` under the legacy stage, `[ranking] shortlist_cap` under the sorted one, both defaulting to 3). The sorted stage caps the **shortlist** and not the results — bound what the model is shown, because it cannot rank what it never saw; do not bound what it returns, because ranking is its job. `group_by = "file"` still collapses to one result per document under both. Lane weights come from `[lane_weights]`; the temporal lane's date range comes from `temporal::parse_date_range_heuristic`, a regex over the query. Results display normalized confidence percentages (0-100%) instead of raw RRF scores. `--explain` prints the retrieval step as well as the fusion step: the query as run, its FTS MATCH expression, per-lane hit counts, and — under a scope — a `scope: all=type/ -> 3 notes` line carrying the filter as the caller wrote it and the number of notes it resolved to, which is the first thing that explains a thin scoped result (#60). Under the calibrated sort, `--explain` also prints the query's BM25 bound and per-term idfs beside the MATCH expression, with each candidate's probability shown as the `calibrated` lane contribution. `rerank_documents()` fetches each candidate's whole chunk, truncates it to `[rerank] max_document_chars` if one is set — it is 0, unlimited, by default since #42 — before prepending any title, so the title cannot be what gets cut, and logs the assembled size at DEBUG — `RUST_LOG=knapper::search=debug` is how `eval/sweep-rerank-chars.py` reads the character counts back.
- `identity.rs` — L1 extraction engine: active projects, key people, current focus, OOO, blocking. `format_identity_block()` for compact session context. `extract_l1_facts()` called after indexing.
- `onboarding.rs` — Interactive CLI UX: welcome banner, vault scan, identity prompts (dialoguer), agent mode (--detect --json, --json). `run_interactive()`, `run_detect_json()`, `run_apply_json()`.
- `cli.rs` — the clap command tree, one variant per capability. A variant's arguments come from its `params` struct, so the command line, the MCP schema and the HTTP route read one declaration; a variant carries a field of its own only where the CLI has an argument the other surfaces cannot have, and `surface::CAPABILITIES` names each of those with its reason (#62)
- `params.rs` — what each capability takes, declared once. One struct per capability, deriving `clap::Args` for the CLI, `Deserialize` for MCP and HTTP, and `JsonSchema` for what an MCP client is shown. Because the three come from one declaration, a parameter cannot be named differently on two surfaces or exist on one and not another. Container encoding still differs where a surface forces it: a GET route reads `?all=a,b` as one comma-separated value, because `serde_urlencoded` reads no sequence (#61). `scope` is the alias of `all` on `Search` and `List`, and every one of the four fields carries tag terms and directory terms alike — a leading `/` reads a field's term as a directory path instead, a trailing `/` its subtree (#65). `List` declares `detailed`, so the outline is one field on all three surfaces; its `limit` is an `Option<usize>` whose absent case is no limit (#68).
- `surface.rs` — the table of what every capability is called on each surface, and the tests that hold the three surfaces to it (#62). One transform gets from any spelling to any other: CLI kebab-case, MCP with `-` written as `_`, HTTP under `/api/` and the kebab name. Three parity tests compare the table with what `cli::Cli::command()`, `KnapperServer::tool_router()` and `http::routes()` register, so a call added to one surface and forgotten on another fails the build. `render_table` generates `surfaces.md`, and a test fails when the committed file is stale

`cli.rs` declares the command tree and `main.rs` dispatches it (async via `#[tokio::main]`). The tree lives in the library so that `surface.rs`'s parity test can walk it under `cargo test --lib` (#62). Every capability is one top-level command: `index` (with progress bar), `search` (with `--explain`, loads intelligence models when enabled, and `--scope`/`--all`/`--any`/`--none` — the four scope operators `list` takes, tag or directory terms alike, scoping the query to the notes they admit (#60, #65), and `-n/--top-n`, which defaults to `top_n` in `config.toml` on all three surfaces), `read` (a note's content, or one of its sections with `--section`, its heading line included; `--metadata` returns the note's frontmatter, its incoming and outgoing links, and its size instead, and cannot be combined with `--section` (#80, #81)), `list` (scope operators as above, `--scope` an alias of `--all`; the output is one bare path per line, so `wc -l` is the total, and `--detailed` puts each note's heading outline under its path, an ATX heading as its `#` markers and a promoted bold line in its bold form), `tags` (the vocabulary, whole or under one term with `--under`), `vault-map`, `create`, `update` (one edit as `--section`/`--property` + `--mode` + `--content`, or the whole grammar as a JSON `--edits` list), `delete` (`--mode soft|hard`), `move` (`--new-folder`), `archive` (`--undo` restores), `reindex-file`, `status` (index statistics, intelligence state, date coverage, and the edge and wikilink counts), `health`, `identity`, `init` (`--mode detect|apply`, or the interactive onboarding flow when no mode is given), `migrate` (`--mode preview|apply|undo` for PARA vault restructuring), and the four that configure the process rather than the vault: `configure` (`--enable-intelligence`, `--disable-intelligence`, `--model`, `--register`, `--add-api-key`, `--list-api-keys`, `--revoke-api-key`, `--setup-chatgpt`), `models`, `clear`, `serve` (MCP stdio server with file watcher + intelligence + optional `--http`/`--port`/`--host`/`--no-auth` for HTTP REST API).

## Key patterns

- **The keyword lane reads the chunk table:** `chunks_fts` is an FTS5 **external-content** table over `chunks`, declared over `text` plus whichever of `heading_path` / `tags_text` `[fts]` enables, and kept in step by three sync triggers (#37). It stores an index and no text of its own, so #11's bug class — the keyword index holding a different string from the chunk — is unreachable rather than fixed, and the triggers are the only writer: a chunk row inserted, updated or deleted by any path updates the index, including the delete SQLite performs itself when `files` cascades. `'rebuild'` reproduces the trigger-built index's postings and BM25 scores exactly; the *bytes* differ, because an incremental write leaves one segment per batch where a rebuild writes a single merged one
- **5-lane hybrid search:** Queries run through up to five lanes — semantic (sqlite-vec KNN embeddings), keyword (FTS5 BM25), graph (wikilink expansion), cross-encoder reranking, and temporal (date-range scoring). Lane weights come from `[lane_weights]` and default to the vector the #57 pool cells measured; the graph lane is held at or below the content lanes (issue #9), a weighting set when graph expansion excluded the seed files and so could never accumulate RRF agreement. It no longer excludes them (#29), and the weights have not been revisited since. Under the default sorted stage the two content lanes are fused by RRF into a shortlist, the graph and temporal lanes fill their reserves in it, and one absolute scorer sorts what results: the cross-encoder when one is configured, otherwise the calibrated logistic over normalized cosine and BM25 (spec 2026-08-30). `mode = "legacy"` is the five-lane RRF control, the cross-encoder among the voters. The temporal lane activates on a date range parsed from the query by regex
- **Vault graph:** `edges` table stores directional wikilink edges (one per `[[link]]`; the reverse edge exists only when the target links back). Built during indexing after all files are written. An edge is **owned by its source file's content**: only that file's re-index may create or destroy it, which is why the re-index path calls `delete_outgoing_edges_for_file` and only file *removal* calls `delete_edges_for_file` (both directions). Both `edges` columns CASCADE off `files(id)`, so re-indexing must not delete the row either — see `index_file` step 5. Wikilinks that resolve to no file are recorded in `unresolved_links`.
- **Graph agent:** One PPR iteration out of the seed chunks, following wikilinks in either direction — outgoing links and backlinks (`Store::incident_wikilink_edges` returns both, oriented near-end-first, in one indexed fetch for the whole frontier). `α` damps each iteration and is inert at one. The lane does not read the query at all: its old admission filter was a weaker second copy of the FTS lane, scoped to one file. Output is capped at `max_chunks_per_file` per document and truncated to 20, both cuts on accumulated mass
- **Smart chunking:** Break-point scoring algorithm assigns scores to potential split points (headings 50-100, code fences 80, thematic breaks 60, blank lines 20). Code fence protection prevents splitting inside code blocks. This scoring is `smart_chunk`'s own, off the live chunking path: `structure_chunk` packs whole paragraphs to `TARGET_TOKENS` and emits a single over-budget paragraph or table whole, with no fixed size ceiling on it — the real ceiling is the embed model's input wall, enforced downstream by `split_oversized_chunks` (#75)
- **Edge granularity:** an edge's source is the chunk whose text held the link, so `build_edges_for_file` reads the file's chunks from the store and **requires them to be inserted already**. A link the chunker never sees (frontmatter) is attributed to `DOC_LEVEL`, which is why it still takes `content`. Target side: `[[Note#Heading]]` resolves to the chunks under that heading, and a plain link — or a heading that has since been renamed — becomes `DOC_LEVEL` rather than nothing. `indexer::backfill_edges_from_chunks` re-derives the whole table from `chunks.text` with no vault read, which is how a pre-#28 store adopts the grain; `Store::needs_edge_backfill` is the flag the migration raises
- **Incremental indexing:** `diff_vault()` compares file content hashes in SQLite against disk. A changed file keeps its `files` row — and therefore its id, and therefore every backlink keyed on that id — while its chunks, vectors, FTS rows and *outgoing* edges are cleared and recomputed; `insert_file` upserts on `path`. `writer::move_note` likewise moves the row with `update_file_path` rather than replacing it. `an_incremental_edit_and_a_full_index_agree_on_the_edges_table` (`indexer.rs`) is the invariant. Content hashes are blind to everything *outside* the file, which is what `fingerprint` covers: a chunker constant, the embedding prompt, the link resolver or the FTS schema can all change with no file changing, and `run_index_inner` reconciles those before it diffs anything
- **sqlite-vec for vector search:** Vectors stored in a `vec_chunks` virtual table (vec0). KNN search via `vec_distance_cosine()`. Real deletes — no tombstone filtering needed during search
- **Write pipeline:** 5-step process for creating/modifying notes: (1) resolve tags via fuzzy matching against the tag store, (2) discover potential wikilinks via exact + fuzzy matching, (3) suggest folder placement via centroid similarity, (4) atomic file write (temp + rename for crash safety), (5) immediate index update (embed + insert into sqlite-vec + FTS5 + edges)
- **Warm sync (file watcher):** OS thread watches vault via `notify-debouncer-full` (2s debounce), on a backend chosen by `[watcher].backend` — native inotify/FSEvents, or a `PollWatcher` fallback for bind-mount/overlay/network filesystems inotify cannot service, auto-detected via `statfs` (#83). Events sent over `tokio::mpsc` to async consumer. Two-pass processing: mutations then edge rebuild. Move detection via content hash matching. Placement correction learning on file moves (centroid adjustment + frontmatter stripping). Startup reconciliation catches changes since last shutdown
- **Fuzzy link matching:** Sliding window of N words over content, compared via `strsim::normalized_levenshtein` with 0.92 threshold. First-name matching for People notes (uniqueness check, 650bp confidence, suggestion-only). Overlap resolution: exact > alias > fuzzy > first-name
- **Centroid updates:** Online mean math (`adjust_folder_centroid`). Incremented on file add, decremented on file remove. Full recompute during bulk indexing
- **Docids:** Each file gets a deterministic 6-char hex ID. Displayed in search results
- **Vault profiles:** `knapper init` auto-detects vault structure and writes `vault.toml`
- **Two absolute scorers:** the sorted stage sorts the shortlist by a probability, and which scorer produced it depends on what is configured. Qwen3-Reranker-0.6B scores query-document relevance via Yes/No logit softmax over the top-30 candidates, reading each candidate's whole `chunks.text` rather than a lane-dependent preview — which is why it is roughly half the cost of a reranked query (`eval/probes.md`, #14); under `mode = "legacy"` it is a 4th RRF voter instead. With no cross-encoder configured — the default install — the calibrated logistic scores the same slot with no model call, from each candidate's cosine and its BM25 against the query's own upper bound (spec 2026-08-30). Each scorer carries its own floor, because each was fit against its own scores
- **llama.cpp backend:** Global `LlamaBackend` singleton via `OnceLock`. `LlamaModel` is `Send+Sync`, `LlamaContext` is `!Send` (created per-call). Metal GPU auto-detected on macOS. Models download from HuggingFace on first use with progress bar. Every context sets `n_threads` + `n_threads_batch` from `resolve_n_threads`, which defaults to **physical cores** — llama.cpp's library default is a flat `GGML_DEFAULT_N_THREADS = 4` on any machine, and counting logical CPUs instead is measurably *worse* than that on an SMT box (issue #20)
- **Prompt formatting:** `PromptFormat` auto-detects model family from GGUF filename and applies asymmetric prefixes in `embed_query` (queries) and `embed_batch` (documents). The `EmbeddingGemma` pair is the one its model card documents — `<bos>task: {task} | query: …` and `<bos>title: {title | none} | text: …` — and each half is selectable, `[embedding_prompt] document` / `query`, with `legacy` restoring nomic-embed-text's `search_query:` / `search_document:` convention as the control (issue #10). The `<bos>` is in the template because `str_to_token` is called with `AddBos::Never`. The `title:` field holds whatever `[embedding_prompt] document_title` names, composed per chunk by `prefix::embed_inputs` (issue #36). Which document template built a store is hashed into `embedding_fingerprint` from `PromptFormat::template_id`, and the title selection is hashed beside it, so switching either re-indexes; the query half reaches no fingerprint. A note's content is a document, so `placement` embeds it through `embed_batch` rather than as a query

## Data directory

`~/.knapper/` by default, resolved by `Config::data_dir()` through `config::resolve_data_dir`: the `--data-dir` override (a `OnceLock` set once in `main` before any read) wins, then `KNAPPER_HOME` (used verbatim, empty reads as unset), then `~/.knapper`. Everything derives from it, so one override moves them together (#77). Contains the store (SQLite with FTS5 + sqlite-vec + edges), `models/` (GGUF models + tokenizers), `vault.toml` (vault profile), `config.toml` (user config with intelligence toggle + model overrides). `config::db_path()` resolves the store file: `knapper.db` for a fresh directory, with a read fallback to a legacy `engraph.db` left by a store from before the rename.

Single vault only. Re-indexing a different vault path triggers a confirmation prompt.

- `ureq` (2.12) — blocking HTTP client (native-certs + json features). Model download in `llm.rs` and the optional API embedder in `embed_api.rs`

## Testing

- Unit tests in each module (`cargo test --lib`) — 1014 tests, no network required. `MockLlm` stands in for the embedder and the cross-encoder, so the write, index and search paths all run with no model download. There is no `tests/` directory: a test that reaches the shipped code through the same public API the module tests use belongs beside them, and the two `#[ignore]`d files that used to live there asserted against a copy of the v0.6 pipeline
- End to end, against a real binary: `eval/smoke-tags.sh <scratch-home>` drives the CLI, the MCP stdio handshake and the HTTP endpoint against a store seeded with no model. It uses `target/release/knapper` without building it, so build first or a stale binary answers
- Build requires CMake (for llama.cpp C++ compilation)

## CI/CD

- CI: `cargo fmt --check` + `cargo clippy -- -D warnings` + `cargo test --lib` on macOS + Ubuntu. Ubuntu step installs CMake. **Manual dispatch only in this fork** (`gh workflow run ci.yml`) — it does not run on push or PR, so those three commands are the local gate before every commit.
- Release: native builds on macOS arm64 (macos-14) + Linux x86_64 (ubuntu-latest). Manual dispatch only (`gh workflow run release.yml -f tag=v0.9.x`); it does not fire on tag pushes
- Homebrew: `mightytribble/homebrew-tap` — formula builds from source tarball. Depends on `cmake` + `rust`.

## Common tasks

```bash
# Run tests (requires CMake)
cargo test --lib

# Build release
cargo build --release

# Release: tag, push, then dispatch the workflow manually with the tag as input
git tag v0.9.x && git push origin v0.9.x
gh workflow run release.yml -f tag=v0.9.x

# Enable intelligence (downloads ~1.3GB)
knapper configure --enable-intelligence
```
