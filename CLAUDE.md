# knapper

Local hybrid search and MCP retrieval for Obsidian-format vaults. Rust CLI + MCP server. llama.cpp inference with Metal GPU. MIT licensed.

## Architecture

Single binary with 43 modules behind a lib crate:

- `coalesce.rs` — the query-time transform that presents a document's abutting chunks of one section as one result block, after the ranking stage; `search.rs`'s `finalize_search_output` calls it, so it runs whether or not the cross-encoder ran (#39). A run carries a `root` heading path and admits an abutting chunk whose path is the root or descends from it; a chunk the root descends from widens the root instead, and the loop runs to a fixed point, so which member ranked highest cannot decide the block. `within` compares path segments and never characters, so `Foo` does not swallow the sibling `Foo Bar`. The merge stops at a sibling section because the rule rests on a section being one topic — a subsection subdivides that topic and a sibling starts a new one — and before #101 the run was `seq` alone, which merged across a heading and then labelled the block with a section that had not matched. `merge_block` names the block from its leading member, which is also the shallowest, since a section precedes the subsections it contains (#101). `blocks` is the grouping itself, member indices in output order, and `coalesce_adjacent` is that plus the merge — it is public because `search.rs` counts blocks to honour `top_n`, and a second way of counting them would be a copy of the run rule that could drift (#102)
- `config.rs` — loads `~/.knapper/config.toml` and `vault.toml`, merges CLI args, provides `data_dir()`. Includes `intelligence: Option<bool>`, `group_by` (retrieval granularity — `file` collapses each note to one result under both stages), `max_chunks_per_file` (how much of one note a single retrieval lane may contribute, read **only under `[ranking] mode = "legacy"`** — the sorted stage caps the lanes with `[ranking] shortlist_cap`, which defaults to 8 — a quarter of `candidates`, because that stage's rows are shown to a model rather than counted as votes. Neither bounds the *results*: that is `[ranking] per_note_cap`. `0` is unlimited in all three), `[embedding_prefix]` (contextual prefix composition, off by default), `[embedding_prompt]` (**EmbeddingGemma's templates and nothing else** — `config::section_note` says so above the header, because every key here is inert under another family and the failure is silent (#8); `document` and `query`, which prompt template each half of an asymmetric embedding model is fed through — both default to `documented`, the model card's own format, and `legacy` on either side is nomic-embed-text's convention and the control it was measured against; `document` is a fingerprint component and changing it re-indexes, `query` costs nothing; `document_title` is what fills the document template's `title:` field. `none` is the default: the literal the model card gives for a document with no title. `breadcrumb` is design §5.4's rule, `Note Title > H1 > H2 > H3`; it holds every tracked answer at its rank, and #38 measured it against `none` with the rule's other two limbs on — below the answers the two are a draw on the six positive queries, and `breadcrumb` scores four of the eleven negatives higher, which is what decides it. It does not ship, and it is the closest call in `eval/probes.md`. `note` is the note's title alone and must not be used, because it pushes the exact-name answer out of the top 20, which is issue #2's failure with a shorter prefix. The key is a fingerprint component, so a change to it re-indexes. The breadcrumb still reaches the index through the keyword lane (#37) and the cross-encoder's input (#30), and both of those limbs are measured gains — see `eval/probes.md` (#36, #38)), `[ranking]` (`mode = "sorted" | "legacy"`, which ranking stage runs — `legacy` reproduces pre-#30 output byte for byte and is the control the change was measured against; `retrieval_width`, how many rows each content lane fetches — default 60, which is what the lanes fetched at `top_n = 20` when the width was `top_n * 3`, and the width every table in `eval/probes.md` was measured at. It decides which chunks the cross-encoder can see; `top_n` truncates the output and nothing else (#49). The value is query-time and reaches no fingerprint, so a sweep costs no index work; `candidates`, `graph_reserve`, `temporal_reserve`, `shortlist_cap`, `tiebreak`; `answer_floor`, the score below which a candidate is not an answer — default 0.30, fit against the 17-query pool in `eval/probes.md`; `0.0` removes nothing and is the control. `per_note_cap` limits how many sections of one document appear in the results. The default is 0, which means no limit. It ships as a key so that §9.1 against #30 needs a sweep and not a code change. `coalesce_adjacent` presents a document's abutting chunks of one section, and of the subsections below it, as one block after the ranking stage — query-time, reaching no fingerprint. It stops at a sibling section (#101). The default is on; `false` is the byte-exact per-chunk control (#39)), `[lane_weights]` (what each lane's rank is worth to RRF fusion — `semantic 1.0 / fts 1.0 / graph 0.8 / rerank 1.0 / temporal 0.0`, the best configuration the seventeen pool cells of #57 measured. Query-time, reaching no fingerprint, so a sweep is a config edit with no index work. Under the default ranking stage the cross-encoder sorts the shortlist, so `semantic` and `fts` are the two that decide anything; the rest are read by `mode = "legacy"` alone. `graph` stays at or below the content lanes because graph results are disjoint from theirs and can never accumulate RRF agreement — issue #9), `[rerank]` (`document_title`, prepends the file's title to a candidate before the cross-encoder scores it — off by default, and worth two ranks on one probe under the sorted stage; `max_document_chars`, the ceiling on how much of a candidate the cross-encoder reads — **0, unlimited, by default** since #42: #25 fit a 1000-char cap on a CPU build for 12.3% of query time, and on CUDA the same cap saves 3.6% while truncating 14.8% of the corpus, including the sentences that answer probes 2 and 7. It stays settable, because #25's trade still holds on a CPU build; distinct from `models.rerank`, which only names the model), `[fts]` (what the keyword lane indexes beside the chunk body and how `bm25()` weights it — `heading_path` ships **on** at weight 1.0. It returns `## Level 4 Silence` to probe 3, an answer #36's embedding limb dropped — and #38 removed that limb, so the column's measured gain is gone and issue #41 is the probe that decides its default; `tags` ships **off**, because a tag records an attribute of a note rather than something the note discusses, so it drops probe 2's most direct answer and gives the adjacent negative a 97.06% result — see `eval/probes.md` (#37). Both flags are `fts_fingerprint` components, because the fingerprint hashes the declaration they build, so switching one rebuilds the keyword index in 0.1 s with no vault read and no model; the weights are query-time and reach no fingerprint, so a weight sweep costs nothing. `heading_path = false, tags = false` is the control and reproduces the pre-#37 binary exactly), `[models]` section for model overrides plus `n_threads` (llama.cpp threads per forward pass; unset means physical cores — see `llm::resolve_n_threads`). `models.embed = "gemini:<versioned-id>"` selects the external API-backed embedder; the local `hf:`/absent form is unchanged. `[models.embed_api]` holds that backend's non-secret knobs — `dim`, `timeout_secs`, `max_retries`, `endpoint`. The key is env-only, read from `GEMINI_API_KEY`, and never written to config. `chunk_min_chars`, the shortest section body that becomes a chunk of its own — a shorter section merges into the preceding chunk of the same file, keeping its heading line inside the merged body so its terms stay in the keyword index, and the merge stops at `TARGET_TOKENS`. The unit is characters because the chunker estimates `chars / 4`, so design §5.4's 30 tokens is 120. It is a chunker-digest component, so changing it re-indexes — and the digest moves at 0 too, so every store re-indexes once on the upgrade. **The default is 120**: it takes the eval corpus from 1598 chunks to 1461 and its 72 sub-60-character scaffolding rows to none, and the pool reads nothing against it — every negative holds or falls, every responsive set holds its coverage. `0` is the control and reproduces the pre-#43 chunking exactly (#43), `promote_bold_headings`, whether a bold-only line opens a section — a promoted line is one bold span and nothing else (`**Text**`, `__Text__`, or either with a single colon after the closing marker), so a table row, a list item and a `**Rank**: S • **Levels**: …` preamble are not one. It is deeper than any `#` heading and an ancestor of nothing, so the enclosing heading stays in the breadcrumb, the next promoted line ends the section, and the next `#` heading of any depth ends it too. The raw line stays at the head of the chunk body, so the keyword index reads `**Spells**` and only the breadcrumb reads the stripped `Spells`; a promoted line with no body of its own is not promoted, because a flat construct has no descendants to carry its text. Like `chunk_min_chars` it is a chunker-digest component, so changing it re-indexes. **The default is `true`**, which is the repository owner's ruling and not the measurement's reading: the rule sharpens probes 2 and 7 onto chunks that read as the answer alone, and it costs probe 3 three of its five answers to a flood of per-creature `**Spells**` rows whose mechanism is not diagnosed. `false` is the control and reproduces the pre-#44 chunking exactly (#44), `carry_orphan_headings`, whether a bodyless `#` heading whose line no descendant breadcrumb and no promoted-line carry keeps is folded into a neighbour rather than dropped — a same-level sibling forward into the next section's text, a shallower heading or the end of the file backward onto the previous chunk's, and a file that is nothing but headings into one chunk. The line reaches `chunks.text` only, never a breadcrumb, so its terms stay in the keyword index without renaming any section. Like `chunk_min_chars` it is a chunker-digest component, so changing it re-indexes. **The default is `true`**; `false` is the control and reproduces the pre-#54 chunking exactly (#54), and `[watcher]` section (`backend` = `auto` | `native` | `poll` and `poll_interval_secs`, the warm-sync file-watch backend — `auto` polls only on a filesystem inotify cannot service, `KNAPPER_WATCHER_BACKEND` overrides, #83), and `[calibrated]` (calibrated score fusion for the model-free path, spec 2026-08-30 — `enabled`, default `true`, read only when `[ranking] mode = "sorted"` runs with no cross-encoder configured, and inert with one configured; `false` sends a no-model build to the legacy stage instead, byte for byte, the control; `semantic` 20.777, `keyword` 13.377 and `intercept` -8.762, the pin-fit logistic's three coefficients — 33 tier-1 positives against 1228 labeled negatives, leave-one-query-out validated, provenance `eval/calibrated-fusion-report-2026-08-30.txt` via the refit tool `scripts/calibrated-fusion-eval.py`. They are that tool's `fused-raw` fit, which is the variant `calibrate::probability` computes: it multiplies a raw cosine, and the tool fits three anchored features beside it whose coefficients measure a quantity this engine never forms (#8); `floor` 0.75, the probability below which a candidate is not an answer, `[ranking] answer_floor`'s analog for this path — `0.0` removes nothing and is the floor's own control. **The four are EmbeddingGemma's fit rather than a global default, and they are one fit**: cosine is one model's similarity scale, and the floor is a threshold read off it, so another `models.embed` is the user's to refit and `config::section_note` says so above `[calibrated]` in the generated file. For the two embedders `llm::known_embedders` names beside the default, the fit is taken: `config::section_trailer` writes each one as a commented block **below** the section's keys, so uncommenting it sets the keys, where the same lines above the header would set them in the table before (#8). Scaling the weights alone moves the boundary rather than rescaling it — at `semantic = 11` the floor asks `cos >= 0.8964`, above every positive the fit was built from (#103). All five keys are query-time and reach no fingerprint, so a sweep is a config edit with no index work). `[http] request_timeout_secs` is the request timeout, 60 by default and `0` for none; `/api/index` and `/api/init` are never timed out. A config table this version no longer reads — `[http.plugin]`, `[identity]`, `[memory]` — still loads and is named once at load through `Config::retired_tables`. `Config::save()` writes back to disk by **editing the file rather than rewriting it**: it writes a key whose value differs from its default, and a key the file already holds — an explicit setting is the user's and is kept even at today's default — and leaves everything else, including comments, key order, spacing and a key this build does not know. Serializing the whole struct pinned every shipped default into the user's config, so a release that moved one never reached them (#90). A path with no file yet is given `commented_defaults()`, the whole catalogue commented out under live `[section]` headers.
- `core.rs` — what `knapper serve` holds once and every surface shares: the writer and reader `Store`, the embedder, the cross-encoder when configured, and `config.toml` as it was read at start, in one `Core` that `KnapperServer`, `ApiState` and the watcher each hold a clone of. `with_reader`, `with_core`, and `lock_core` with `CoreLocks::run` (which `with_core` is built from) are the only way to the store and the models: `with_reader` runs a closure against the read-only second connection and `with_core` against the writer, the embedder and the reranker, both on `spawn_blocking`, so no handler blocks a runtime thread. A handler takes no lock itself: the MCP and read handlers go through `with_reader` and `with_core`, and the HTTP write handlers go through `http::core_within`, which calls `lock_core`. `lock_core` is the one place two locks are taken, in one order: writer, embedder, reranker; it answers `CoreLocks`, whose `run` does the `spawn_blocking`, and `with_core` is the two in a row. Dropping an unfinished `lock_core` releases what it took. A read therefore answers during a search, a write, the `index` tool and the startup reconciliation. `pending_events` counts watcher events sent and not yet applied, which `status` reports. `core::blocking` runs disk work that needs no lock, such as `validate` and `init --mode detect`, off the runtime thread. `Core::open` is the startup sequence — store, embedder, dimension check, temp-file cleanup, integrity check, reranker, fingerprint refusal, reader — and `Core::for_test` builds one over a temp-file store for the server tests, whose fixtures live in `core::testing`.
- `fault.rs` — the faults a caller can repair, as one `thiserror` enum of six kinds: `InvalidInput`, `NotFound`, `Ambiguous`, `Conflict`, `StaleIndex` and `ReadOnly`. A `Fault` is built where the fault is known — `tags::check_terms`, the link and cursor resolvers in `store/scope.rs`, `Store::require_file`, `Store::find_file_by_alias`, the mtime check in `writer::update_note`, `fingerprint::verify`, `Core::writable` — carried inside `anyhow` like any other error, and read once at each server with `Fault::of`, which reaches through every `.context()` layer. A site a `Fault` passes through adds context with `.context()` and never `anyhow!("{e} ...")`, which starts a new chain with no source. HTTP maps the six kinds to 400, 404, 400, 409, 500 and 403; MCP to `INVALID_PARAMS` for the first three, `INVALID_REQUEST` for `Conflict` and `ReadOnly`, `INTERNAL_ERROR` for `StaleIndex`; both carry `kind` in the error body. Everything without a kind is the server's own. The rule separating the first two kinds: a scope term, cursor or filter naming nothing is query shape and `InvalidInput`; the `file` or `section` a call addresses naming nothing is `NotFound`. The handler's own parse stage — `parse_scope`, the edit list, a `mode` word — is mapped at the stage, not through the enum.
- `chunker.rs` — structure-first chunking: a file's sections become chunks, packed to `TARGET_TOKENS`. Every piece of a split section is labelled with the heading line the file holds, and that line is what the piece's `text` opens on: a label naming a section the file does not have cannot be addressed by `read --section`, and an `update --section` round trip writes it into the note for real (#139). `split_oversized_chunks` runs over what `emit_section` emitted, so a marker added there compounded on a piece the packing budget had already cut. Which piece a chunk is belongs to the index, and `seq` records it. `emit_section` decides what becomes a chunk, and a section whose body is under `chunk_min_chars` is not one: it merges into the preceding chunk of the same file, heading line included, and the merge stops at `TARGET_TOKENS` (#43). The minimum reaches a section's *pieces* too: a short leading piece that a split would otherwise flush as a stub row of its own is folded forward into the following paragraph, and the combination is emitted whole, so the heading leads real section content — never backward, since a first piece's preceding chunk is a different section (#51). `structure_headings` decides what counts as a heading at all: every `#` heading, and — when `promote_bold` is on — every bold-only line, at a level deeper than any `#` heading so the ancestor stack treats it as flat (#44). `structure_headings` is `markdown::headings_with_promotions` with the bodyless promotions dropped: a promoted line with no body of its own starts no chunk, because a flat construct has no descendants to carry its text, and it is still a section `read --section` and `update --section` address (#44, #69). A `#` heading whose own body is empty is not a chunk: when its next heading is strictly deeper it survives in that descendant's `heading_path`, and when `carry_orphan_headings` is on and no such descendant keeps it — a same-level sibling, a shallower heading, or the end of the file — its line is carried instead of lost, forward into the next section's text for a sibling and backward onto the previous chunk's for a shallower one or the file's end, with a headings-only file kept as one chunk (#54). A promoted line is an ancestor of nothing, so a heading emptied by promotion is carried forward into that promoted section's text (#44). `ChunkOptions` carries `chunk_min_chars`, `promote_bold_headings` and `carry_orphan_headings` as one value, so no path that chunks a file can take one setting and forget the other — a note written through the write pipeline at one setting and re-indexed at another is cut into two different sets of rows, and nothing downstream can tell. `structure_chunk` packs whole paragraphs to `TARGET_TOKENS` and emits a single over-budget paragraph or table whole rather than tearing it; `split_oversized_chunks()` is the sole place a block is torn, and it tears only above the embed model's real input wall (`EmbedModel::max_context`), on sentence boundaries with `OVERLAP_TOKENS` of overlap, rather than at a fixed size (#75). Every number that decides a boundary lives in `chunker::limits` rather than inline, because `chunker_fingerprint` hashes them (#31) — changing one there is enough to make the next index rebuild, with no second place to remember
- `docid.rs` — deterministic 6-char hex IDs for files (SHA-256 of path, truncated). Shown in search results for quick reference
- `llm.rs` — ML inference via llama.cpp (Rust bindings: `llama-cpp-2`). Two traits: `EmbedModel` (embeddings; `embed_batch` takes `EmbedDoc` pairs, so the `title:` field is per document rather than per model — issue #36; `dim` and `token_count` size vectors and budget chunks, and `max_context()` reports the model's real-token input wall, read from the GGUF at load (`n_ctx_train`), falling back to `FALLBACK_MAX_CONTEXT` when the model reports none — it is the ceiling `split_oversized_chunks` enforces, issue #75) and `RerankModel` (cross-encoder scoring; `rerank_batch` takes the whole candidate set so an implementation can set up once). Two llama.cpp implementations: `LlamaEmbed` (embeddinggemma-300M GGUF on Metal GPU) and `LlamaRerank` (Qwen3-Reranker-0.6B for relevance scoring). Nothing generates text — the orchestrator that did is gone (#59). Global `LlamaBackend` via `OnceLock`. A `LlamaContext` cannot be a struct field (it borrows the model) but does span a whole batch: `LlamaEmbed::embed_formatted` and `LlamaRerank::rerank_batch` each build one and clear the KV cache between items. Also: `MockLlm` for testing, `HfModelUri` for model download, `FlexTokenizer` (HuggingFace tokenizers + shimmytok GGUF fallback), `PromptFormat` for model-family prompt templates (each half of the EmbeddingGemma pair selected by `EmbeddingPromptConfig`, `EmbedTask` naming the task a query prompt asks for, and `DocumentTitle` naming what fills the document half's `title:` field). `PromptFormat` also carries the two things about a family that are **not** its text (#8), because both are wrong by default for anything but EmbeddingGemma: `forward_pass` is which llama.cpp call runs the graph — `encode` hands it a null memory context, so a decoder-only embedder whose graph opens with `build_attn_inp_kv()` dereferences that null and segfaults, and `decode` is what supplies the cache; `add_special` is what `str_to_token`'s `AddBos` really gates, llama.cpp's `add_special`, which decides the model's declared **trailing EOS** as well as its leading BOS. EmbeddingGemma keeps `Encode` and `Never` — it pools the mean, builds no cache and writes its own `<bos>` into the template, so every stored vector is unchanged — while Qwen3-Embedding needs `Decode` and `Always`, because it pools the **last** token and its GGUF declares `add_bos_token = false, add_eos_token = true`. `known_embedders` is the menu `knapper models` prints: the shipped default first, then the two Qwen3 embedders, each with the width, context and download size its GGUF reports, so a choice can be made before the download. It decides nothing — `models.embed` still takes any `hf:` GGUF, and the width, the context and the format all come from the model at load. `EmbedModel::fingerprint` and `RerankModel::fingerprint` carry model identity to `fingerprint::Fingerprints` — computed once at load, because they hash the GGUF's bytes
- `embed_api.rs` — the optional API-backed embedder (#84). `ApiEmbedder<P: EmbedProvider>` implements `EmbedModel` and owns the `ureq` client, batch splitting at the provider's cap, bounded retry with backoff on 429/5xx/transport errors, and L2 normalization of every returned vector. `EmbedProvider` is the small per-provider surface (env var, endpoint, auth header, native dim, input-token ceiling, batch cap, identity, request builders, response parse). `struct Gemini` is the first provider (`gemini-embedding-2`), selected by `models.embed = "gemini:<versioned-id>"` with the key in `GEMINI_API_KEY`. The trait stays synchronous; the call blocks through `ureq` the way local inference does. `llm::load_embedder` routes `models.embed` by scheme and is the one construction path for both backends.
- `fts.rs` — FTS5 full-text search support. Re-exports `FtsResult` from store. BM25-ranked keyword search, weighted per column by `[fts]` (#37). Builds the MATCH expressions the store runs: `phrase_expr` (the whole query verbatim) and `any_term_expr` (each token quoted, joined with `OR`, what the search lane needs — quoting the whole query made it a phrase query that four of five seed probes matched nothing with, issue #22)
- `frontmatter.rs` — a note's frontmatter block as an ordered list of items, each carrying the bytes it was parsed from: one per top-level key, one per comment or blank line between them. A list's own items carry their source text the same way, so adding one item to a list leaves every other item exactly as written — a quoted string stays quoted, a bare number stays a number. Six operations rewrite one item's text, so a write changes the keys it names and leaves the rest of the block, and the whole body, byte for byte. A key that is new is appended in the style the block already uses, or placed by a `KeyPlacement` — `After` or `Before` one of the block's own keys, which is how a vault with a fixed key order writes a key a note did not have. A key the block already holds keeps the place the file gave it, so a placement places and never moves, and an edit can be re-run; an anchor the block does not hold is refused rather than appended. `Before` steps back over the comment lines that introduce its anchor and stops at a blank line, because a comment belongs to the key below it and a blank line separates groups (#113); a value written fresh takes the quote character the key's own values already use, then the first one the block uses anywhere, then `"`, which is what Obsidian's own property writer emits — a value re-emitted in the other quote character changes a line whose value did not change, and single quoting cannot hold a line break or a tab at all, so a value carrying one takes `"` whatever the key prefers (#112); an empty list is written `[]`, because block style with no items reads back as null; a value no line edit can address — a nested mapping, an anchor, a block scalar, or a flow list with text after its closing `]` — refuses the write and names what it found. `Block::parse` returns `Ok(None)` for a note with no block and an error for one that cannot be edited, so `parse_or_open` never writes a second block over a broken one (#92)
- `ranking.rs` — the ranking stage (issue #30). Builds the shortlist the cross-encoder is shown and then lets it **sort**, instead of fusing its score in as a fourth lane. `build_pool` takes content anchors in fused order and graph anchors in reach order against declared `Reserves` (`candidates` 32, `graph_reserve` 8, `temporal_reserve` 4), backfilling either way — a quota is a ceiling, so an unfilled reserve is handed back rather than left empty. Every `Candidate` carries its provenance (`rrf_rank`, `graph_rank`, `admitted_by`), which is what makes `PoolShape` able to answer #30's three separate questions: how many graph candidates existed, how many entered the pool, how many reached the output. `sort_by_rerank` orders by whichever probability filled `rerank_score` — the cross-encoder's or the calibrated logistic's — with `Tiebreak` deciding exact ties only; `degraded_interleave` is the documented 3:1 fallback for a *configured* cross-encoder failing at call time, and its confidence is a **position, not a probability** — it is not what runs for a build with no cross-encoder configured, which the calibrated logistic sorts instead (spec 2026-08-30). `into_fused` names whichever lane sorted the pool, `"rerank"` or `"calibrated"`, so `--explain` credits the right one instead of calling every sort score a rerank score. `apply_answer_floor` then removes every candidate whose sort-lane probability scored below its own floor — `[ranking] answer_floor` for the cross-encoder, `[calibrated] floor` for the logistic (issue #34). It applies to each candidate, so it both empties a response that has no answer and removes the low-scoring results below a correct one. It skips a candidate whose `rerank_score` is `None`, because a position is not a probability. An empty result set gives `NO_RELEVANT_CONTENT` on the CLI, and as a second MCP content block next to the empty array
- `calibrate.rs` — the calibrated-fusion arithmetic (spec 2026-08-30): FTS5's own `idf`, clamped the way FTS5 clamps it; the query's BM25 upper bound, `(k1 + 1) · Σ idf` with `k1 = 1.2` (FTS5's own constant) — the `[fts]` column weights do not enter it, because each term's contribution saturates at `idf · (k1 + 1)` and FTS5 folds a weight into the frequency before that ratio, so a heavier weight moves a row's score toward the same ceiling instead of raising it, and this is also the formula `scripts/calibrated-fusion-eval.py` fits the shipped coefficients with; `normalize_bm25`, the `[0, 1]` fraction of that bound a candidate's raw BM25 reached, clamped rather than inverted outside it; and `probability`, the three-coefficient logistic `σ(w_s·cos + w_k·bm25n + b)` over `[calibrated]`'s weights. Pure math — no store, no model, no I/O — so `search.rs`'s `apply_calibrated_scores` is the only caller and every formula is testable against hand-computed values
- `fusion.rs` — Reciprocal Rank Fusion (RRF) engine. Merges semantic + FTS5 + graph + reranker results, keyed on `(file_id, chunk_seq)` so one document can contribute several sections. `cap_per_file` bounds that share; a cap of 1 is file-level grouping. Supports per-lane weighting from `[lane_weights]`, `--explain` output with per-lane detail
- `markdown.rs` — what a file's headings are, and which one a caller named. `parse_headings` reads the ATX headings; `headings_with_promotions` adds every bold-only line at `PROMOTED_LEVEL`, which is the set `find_section` addresses and `list --detailed` enumerates, so a caller can name the section the outline printed (#69). A `Section` is its `heading` and its `body`, and the body is what sits below the heading line, blank separators excluded, because that is what `writer::apply_section_edit` writes back (#96). A section is its subtree: `section_at` ends the body at the next heading at or above the section's own level, so a `##` owns the `###` sections under it, and a read and a write of one section agree on what it holds (#116). `find_section` resolves a name against the file and retries once with every trailing `(cont.)` removed, and only after the literal lookup answered nothing on both heading passes — an index written before #139 labelled a split section's later pieces `## X (cont.)`, so a caller can hold a name no heading matches, while a note that wrote `## Notes (cont.)` itself is still found as itself. `strip_continuation` refuses a name that is nothing but markers. The strip is not in `normalise`, which folds the file's headings as well as the query and would make two real sections one, sending a read — and an `update --section` write — to the wrong one. `find_section` takes a heading's own text — the first of that name at any depth — or its full path from its own root joined with `>`, and it runs both lookups over the ATX headings before the merged set, so an ATX heading keeps precedence over a promoted one of the same name and a partial path resolves nothing. A segment is compared through `bold_heading_text`, so `**Spells**` and `Spells` name one section. `split_frontmatter` splits the YAML block between `---` fences. Powers section-level reading and editing
- `matching.rs` — the literal scan behind `match` (#106). `search` is ranked, budgeted and cut to `top_n`, so it always answers something and cannot report that a string is **absent**; this is the other contract — one literal pattern, every note the scope admits, no ranking, and counts that come back whole when `limit` caps the reported lines. `Query` holds the pattern and folds case unless `case_sensitive`; the pattern is text and never a regex. It compares each line **twice**, as written and as read — `graph::render_wikilinks` supplies the second — because a wikilink is markup the reader of a note never sees, so a phrase spanning one is absent from the raw line and present in the note. Comparing both is what keeps the markup itself findable, which is the query link maintenance asks, and it makes `notes: 0` the stronger answer: the pattern is in neither reading (#118). `word` narrows a hit to one standing as its own word — the characters either side of it are not alphanumeric and not `_` — and is asked of each reading in turn, walking the occurrences rather than taking the first, because a line can carry the pattern inside a longer word before it says the word itself. An edge is tested only where the pattern's own character there is a word character, so `--word "(DNA)"` stays matchable, and those two edge classes are read from the pattern **as written** and never from its folded copy: `İ` is a letter and folds to `i` plus a combining mark, which is not one, so the folded copy would drop the right-hand test and let `İx` answer. Two limits are declared rather than fixed: a script that does not space its words — Han, Kana — makes every neighbour alphanumeric and so rejects nearly every hit, and only wikilinks are rendered, so markup inside a word — `**art**ist` — puts a non-word character beside the pattern in both readings and reads as a word where a reader sees one. Off by default, which keeps the plain substring comparison (#129). `Scanner` is a visitor rather than a returned list, because the scan is exhaustive by contract and reads every row in scope whatever the limit, so materializing the vault's text would be waste — `store::for_each_scan_row_in_scope` streams the rows past it in path and chunk order. It dedups on `(file, part, heading path, line)`, which is what keeps `split_oversized_chunks` from reporting one line twice: an oversized split repeats `OVERLAP_TOKENS` of the previous piece at the head of the next and gives both the same `heading_path`. `notes` is the answer to the absence question and `limit` never truncates it. A `Hit` carries the matched line's **text** and not a file line number, because a chunk row holds no offset into its file and reading one would mean the vault read this capability does not do — `heading_path` is what `read --section` addresses, so a hit is actionable as it stands. It reads **both halves of a note** (#137): `chunks.text` for the prose and `files.frontmatter` for the YAML block, which the chunker strips and which is therefore in no chunk row. Reading the body alone made `notes` a count of the wrong population with nothing to signal it — an alias, a retargeted `parent:` or a renamed property key was absent from every row the scan read, and a vault with structured frontmatter puts a rename there at least as often as in the prose. `Part` says which half a hit came from, on the wire as `in`, because a frontmatter hit has no breadcrumb and a body chunk under no heading takes the note's own name as its whole one (#46), so a null `heading_path` does not separate them — and the two take different `update` edits, a section `replace` against a property edit (#96). `params::Scan` (`all`, the default, `body`, `frontmatter`) narrows the reading: an alias exists to keep an old name, so "prove no *prose* still calls it X" is a real question. `run` is the one path all three surfaces take, so the guard against a store written before the column lives there rather than on one surface — the CLI loads no embedder and so never reaches `fingerprint::verify`. It refuses an empty pattern, which every line holds
- `health.rs` — vault health diagnostics. Orphan detection (notes with no incoming or outgoing wikilinks), broken link detection (wikilinks pointing to nonexistent notes), stale heading detection (`find_stale_headings`, #99: a `[[Note#Heading]]` whose note resolves but whose heading it no longer holds — not a broken link, so `unresolved_links` never sees it; found from the vault side, so a heading renamed outside knapper counts), stale note detection (notes not modified within configurable threshold), tag issues (a note under a Work folder that carries no `work` tag). Returns structured health report
- `validate.rs` — disk-truth markdown checks (#70), and the property hygiene rules (#66): `check_properties` per file (an unquoted frontmatter link, a declared-type mismatch) and `PropertyTally` across the walk (mixed kinds, near-duplicate names, and on the whole vault a declared name no note carries)
- `context.rs` — context engine. Three functions: `context_read` (four modes on one `include` enum, #80 and #130: `content`, the default, returns a `NoteContent` — the whole note's body, or one section's body with its `heading` and `level` named beside it rather than carried in the content, so that what a read returns is what an `update` takes back, #96; `frontmatter` returns a `NoteFrontmatter`, the note's YAML alone with none of the link work, which is the point of it — the two link lookups and the property read are what makes a metadata read expensive, and a caller wanting four lines of YAML should not pay for the graph to get them; `all` is `Content` with its `frontmatter` filled, **not a variant of its own**, so the default mode's JSON is unchanged by the mode existing, and the key is present even where a note has no YAML, since an absent key would read as a `content` reply; `metadata` returns a `NoteMetadata`, the note's frontmatter, links and size, plus the note's property rows and the property names behind each link (#66). `frontmatter` and `metadata` answer the whole note, so both reject a section — `frontmatter` refuses rather than ignores it, because a caller who meant `all` would otherwise get a plausible answer with the section silently dropped — while `content` and `all` take one, frontmatter being note-level and a section body section-level. An enum and not a set of booleans, so no caller can ask for two modes at once; it replaces the `metadata` boolean outright on all three surfaces rather than sitting beside it. All four are one `ReadResult`, serialized untagged. A section is a parameter of the capability, not a capability of its own, #62), `context_list` (every note a scope admits, each row carrying the note's `aliases` beside its `tags` (#142), in path order — the store's `ORDER BY f.path`, so a folder's notes arrive together and a subtree reads as one block. An absent limit is no limit, because a caller that wants less names a scope or a limit and one cap on one surface would make the field mean two things; `0` answers none. `after` is the last path a page answered, and the next page starts after that row's sort key rather than after a count of rows, so a note created or deleted between two pages repeats or skips no other note — under a `links_in` sort the key is the note's current count and its path, so a path the vault no longer holds is refused rather than guessed (#143). `detailed` adds each note's headings, ATX and promoted bold lines alike, a promoted one carrying no `level`, read from the file with the frontmatter stripped and the line numbers 1-based, because the index cannot answer the outline: a short section merges into the chunk before it, an empty heading emits no chunk, and a promoted bold line sits in `chunks.heading` beside real headings. A file the store holds and the disk does not is listed with an empty outline and no error, #68. Under a `property` term each note also carries the rows that term matched, narrowed by a `links_to` term beside it and absent under `linked_from`, where the matched row belongs to the naming note — `matched_properties` states the rule and answers the whole listing in one query, #66), and `vault_map` (structure overview, and the first call on an unfamiliar vault: folder counts and `total_*` say where notes are filed, and `top_notes` says which ones matter — the ten the vault points at most, `path` and `links_in` only, from `Store::top_linked_files`'s one grouped pass over the edge index rather than `list_files_with_links_in`'s per-file subquery, because ranking on a computed column makes that call's `LIMIT` stop no work. It carries no `chunk_count` or `token_count` beside them: a map is a fixed shape and a caller wanting sizes has `list` (#131). `tagged_notes` is the denominator `top_tags` lacked — a head count read against `total_files` overstates the vocabulary's reach — and `tag_axes` is `Store::tag_axes().len()`, which says whether the vocabulary is a structure or one facet. `recent_files` sorts on `mtime` and not `indexed_at`, because a rebuild reinserts every row in walk order and collapses `indexed_at` into it; `mtime` answers what changed, as of the last index (#138)). `resolve_file` names a note by `#docid`, exact path, basename, then alias, so a filename beats another note's alias (#142). Pure functions taking `ContextParams` — no model loading. Composite bundles over these primitives are #71's vault-defined commands (#73)
- `vecstore.rs` — sqlite-vec virtual table integration. Manages the `chunks_vec` vec0 table for vector storage and KNN search. Handles insert, delete, and search operations against the virtual table. `search_vec` takes an optional tag scope and adds `AND rowid IN (SELECT vector_id FROM chunks WHERE file_id IN rarray(?3))` to the KNN, which vec0 reads as a pre-filter rather than as a cut over an already-chosen neighbourhood, so `k` still means k in-scope rows (#60)
- `tags.rs` — the tag rule. `extract` reads a note's tags from the two sources Obsidian defines, the `tags` property and the `#tags` in the body, which are peers: neither requires the other. A `Tag` carries both spellings — `path` is folded and is the identity, `display` is what the vault wrote — and the path's first segment is its **axis**. Only the path a note carries is returned: `type/undead` does not imply a `type` tag, and a query reads the ancestors out of the path text. The five rejections in the body are an ATX heading, a code fence or span, a URL fragment, a heading inside a wikilink, and an escaped `\#`; three of them fall out of one test, that a tag opens a line or follows whitespace. `resolve_tag` is the write path's fuzzy matcher, reading `SELECT display FROM tags` and comparing one segment against the segments that share a parent, so `type/undead` and `type/undeed` score against each other and `type/undead` and `habitat/undead` do not. `TagTerm` (`Exact`/`Subtree`) is the read-side tag term grammar: `parse_term` reads one leading `#`, a trailing `/` or `/*` as the subtree marker, and folds case; `predicate` compiles one term to one SQL predicate over a `tags` row aliased `t`, a range for `Subtree` so the unique index on `path` serves it, never a `LIKE`. `ScopeTerm` is a tag, a directory (`FolderTerm`, `Exact`/`Subtree` of a vault-root path) or a note (`File`, #144): `parse_scope_term` routes on a leading `/`, and a directory term keeps its case — because `files.path` keeps its — while a tag term folds; `folder_sql` compiles a directory term to a range predicate over `files.path` aliased `f`, the directory's own never-`LIKE` rule (#65). A `/` path ending in `.md` with no subtree marker is a `File`, compiled to `f.path = ?`. The kind is read from the spelling and never from the vault, so `/X` stays the folder and `/X.md/` is the subtree of a folder called `X.md` — this is what lets `list --detailed` answer one note's outline, and `search` and `match` scope to one note, with no parameter beside the scope. `Scope { all, any, none }` is the note-query side, built by `parse`, which errors naming the field when a field holds input and none of it survives parsing; `merge_scope_alias` folds the CLI's and MCP's `scope` alias into `all`. A `Scope` also carries `property` (`PropertyTerm`, `NAME` or `NAME=VALUE`), `links_to` and `linked_from` (`LinkTerm`, a note name that `Store::resolve_scope_links` resolves through the wikilink resolver into a `LinkIds` pair `scope_clauses` takes beside the scope). A link term alone reads `edges`; with a property beside it only links filed under that name count. One value each, on every surface (#66). `check_terms` rejects an `all`/`any` term the vault holds no match for, naming the nearest tag from `resolve_tag` or the subtree of the term itself when that is what would have matched, and the nearest folder for an unknown directory (#65). An unknown file term answers `no such note` as a `Fault::InvalidInput`, which the servers read as a 400 or `INVALID_PARAMS`, naming the vault's spelling of a path that differs only in case, then a note of the same filename in another folder, then the nearest folder (#144)
- `aliases.rs` — the alias rule (#142). `extract` reads a note's other names from the `aliases` key of its YAML block: each list item is one alias, a plain string is one alias with no comma split, a number or boolean item is its text, and a nested or empty item is skipped. Only the plural key is read, the rule `properties::BUILT_IN` follows and the one Obsidian 1.9 keeps. `fold` is lowercase, done in Rust because SQLite's `lower()` folds ASCII only; two spellings that fold to one alias are one alias. A change to the grammar is a `LINK_RESOLVER_VERSION` bump, because the edge pass writes the rows
- `properties.rs` — custom properties (#66). `Kind` is the shape rule's vocabulary: `text`, `number`, `checkbox`, `link`, `empty`. `kind_of` is the rule, and `from_frontmatter` and `from_chunk` are the two sources, each under its owner's grammar — Obsidian's for the block (a quoted `"[[X]]"` is a link, an unquoted one is a nested sequence and writes nothing, a YAML string keeps its type so `"5"` is text where `5` is a number), Dataview's for the body (`Key:: value` with a blockquote, list or task prefix, `[key:: value]`, `(key:: value)`, a top-level comma is a list, an element with wikilinks writes one link row per link). The indexer calls both from `build_edges_for_file`, so every path that keeps edges right keeps properties right; `LINK_RESOLVER_VERSION` covers the grammar. `declared_types` reads `.obsidian/types.json` at call time as a hint, never as a source of rows. `run`/`render_text` are the one path the `properties` capability takes on the three surfaces
- `links.rs` — link discovery module. Three match types: exact basename, fuzzy (sliding window Levenshtein, 0.92 threshold), and first-name (People folder, suggestion-only at 650bp). Overlap resolution via type priority (exact > alias > fuzzy > first-name). An alias entry comes from the `aliases` table through `Store::aliases_for_files`, so the suggester and `read` read one alias grammar and discovery reads no file (#142)
- `writer.rs` — write pipeline orchestrator. four-step pipeline: resolve tags (fuzzy match against the tag store), discover links (exact + fuzzy), atomic file write (temp + rename), and index update, which is also where a file's tag rows are reconciled (#60). The surfaces reach five operations: `create_note`, `update_note`, `move_note`, `archive_note` (with `unarchive_note` behind `archive --undo`) and `delete_note` (soft archive or hard permanent — the soft mode relocates the note and keeps it indexed, so it moves the `files` row rather than replacing it). `update_note` takes one list of edits, which is the whole edit grammar: each edit names a section, a frontmatter property or neither (the body), and carries a mode of replace/prepend/append/remove. A section edit also takes a `heading`, the new heading text, which renames the section it names: the note keeps the heading's own markup, `content` is optional beside it because a rename does not restate the body, and a name another section of the note already holds is refused, since two sections of one name leave both unaddressable by name (#97). A section edit's content is the body below the heading, and content that opens with a heading at or above the section's own level is refused — such a line ends the section rather than fills it, which is how `read`'s old heading-carrying output wrote a note's heading twice and said nothing (#96). A section is its subtree, so an edit of a `##` reaches the `###` sections under it: `owned_headings` is the headings inside a section's span, and a `replace` that carries no heading of its own restates none of them, which is refused because it would delete them and report success — `prepend` writes the lead-in above them and naming a subsection as the section edits it alone (#116). `remove` deletes a section, its heading line and its subtree both, and it reads no content; a rename beside it is refused, since a removed section is not there to rename (#117). `stale_links_for` reads the note's text as well as the edits, because a remove takes headings the edit list does not name and the inbound `[[Note#Heading]]` links to those are stale too (#99, #117). A property edit also takes `after` or `before`, the key a new frontmatter key is placed next to, and naming both is refused; a placement on a section or a body edit is refused before any of the list is applied, the rule `heading` already follows (#113). `apply_note_edits` applies the whole list to the text, so a batch is one file write, one mtime-based conflict check and one re-index (#62). A note's final newline is not a thing an edit names: `keep_final_newline` gives the written text the trailing newline the note had, or takes the one it did not, so a one-line addition is one line of diff (#94). Crash recovery is via temp file cleanup. `inside_vault` is the one check that a vault-relative path a caller names stays in the vault — `create`'s `folder`, `move`'s `new_folder`, `unarchive`'s `file` and the `archived_from` it reads, `reindex-file`'s `file`, and `validate`'s `path` — refused as `Fault::InvalidInput`; it is lexical. `move` trims `new_folder` of `/` as `create` trims `folder`. `create_note`, `update_note`, `archive_note` and `unarchive_note` — the four write paths that touch frontmatter — route it through `frontmatter::Block`, so each writes only the keys it names and leaves the rest of the block alone; `create_note` writes no key of its own beyond the tags it resolved, and files the note under `folder` or at the vault root. `archive_note` writes `archived`, `archived_at` and `archived_from` into the note's own block rather than a tag, and `unarchive_note` removes exactly those three, so an archive round trip returns the file byte for byte — a note with no block gets one while archived and none back afterwards (#92)
- `watcher.rs` — file watcher for `knapper serve`. OS thread producer (notify-debouncer-full, 2s debounce) sends `Vec<WatchEvent>` over tokio::mpsc to an async consumer task that applies them through `Core::with_core`, one file per lock. The producer selects its backend from `[watcher].backend` (`KNAPPER_WATCHER_BACKEND` overrides): `native` is the `RecommendedWatcher` (inotify/FSEvents), `poll` is a `PollWatcher` at `poll_interval_secs`, and `auto` (default) `statfs`-probes the vault and polls only on a filesystem inotify cannot service — overlay, fuse, 9p, nfs, cifs — which is the Docker bind-mount case where native events never arrive (#83). Both backends drive one generic `drive_producer` loop. Two-pass batch processing: mutations (index_file/remove_file/rename_file) then edge rebuild. A removal whose path still holds a file is not a deletion: an atomic save is a rename over the target, and the debouncer synthesizes a removal for it — `writer::atomic_write` writes that way, so taking it at face value evicted the note the pipeline had just edited (#93). Move detection via content hash matching. Startup reconciliation is `enqueue_diff`: the store's file records are read through the reader, the vault is walked and hashed holding no lock, and the diff is queued as per-file events, counted into `pending_events` whole before the first send, so the handshake answers at once and a read answers throughout; a `FullRescan` is the same diff replacing its batch. `run_index_shared` under `serve` has one caller, the `index` capability. `recent_writes` map coordination with MCP server to prevent double re-indexing of files written through the write pipeline
- `serve.rs` — MCP stdio server via rmcp SDK. Exposes 18 tools, one per capability and named the way `surface::CAPABILITIES` names it, with `-` written as `_`: 7 read (search, match, read, list, tags, properties, vault_map) + 5 write (create, update, delete, move, archive) + 5 index and diagnostic (index, reindex_file, status, health, validate) + 1 setup (init). `list` filters by scope operators (`all`/`any`/`none`, `scope` an alias of `all`, tag or directory terms alike) through `tags::Scope`, answers in path order, and carries each note's heading outline when `detailed` is set; `tags` reports the vocabulary, whole or under one term, through `Store::tags_under` — the call an agent makes before it can filter with `list`. The tool is the CLI's `tags` command and the HTTP `GET /api/tags`, one capability spelled per surface (#61, #62). The `search` tool takes the same four operators as its scope, as optional string arrays, and hands them to the pipeline as `SearchConfig::scope` (#60). An unknown directory term answers the same repair as an unknown tag, naming the nearest folder (#65). A client reaches the tools by either lifecycle: one that opens with `server/discover` is answered from `get_info()` and served with no `initialize`, and one that opens with `initialize` negotiates a protocol version, which is what a client before the 2026-07-28 revision sends. The SDK implements both, so `ServerHandler` declares no method for either (#109). KnapperServer holds a `Core` and nothing else; every handler goes through `with_reader` or `with_core`, and `search` calls `search::run_query`, the one body the CLI and HTTP call too. Every handler maps an error through `mcp_err`, which reads the `Fault` kind once: `INVALID_PARAMS` for the caller's input, `INVALID_REQUEST` for a conflict or a read-only server, `INTERNAL_ERROR` otherwise, with `data.kind` naming it; the handler's own parse stage answers through `invalid_params`. `run_serve` takes the `Config` the CLI loaded and reads the file again nowhere; `init --mode apply` writes `vault.toml` and answers `restart_required: true`, because the profile is read once at start. Spawns file watcher on startup. `recent_writes` map prevents double re-indexing of MCP-written files. HTTP mode also serves `/openapi.json`, the document `openapi.rs` generates, with no auth required
- `http.rs` — axum-based HTTP REST API server, enabled via `knapper serve --http`. 19 REST endpoints under `/api` — one per capability, plus the `/api/health-check` liveness probe — declared by `routes()` and checked against `surface::CAPABILITIES` by a parity test, plus `/openapi.json`, which takes no key. `/api/list` takes the scope operators the CLI and MCP take (`scope`/`all`, `any`, `none`, tag or directory terms alike, each one comma-separated string because `serde_urlencoded` reads no sequence), and `/api/tags?under=` is the vocabulary beside it (#61). `/api/list` also takes `detailed=true`, whose value is required because `serde_urlencoded` reads no bare flag. `POST /api/search` takes the same four operators as its scope, as arrays in its JSON body rather than as comma-separated strings, and an error answers the status `fault.rs` maps its kind to, with `kind` beside `error` in the body: `From<anyhow::Error> for ApiError` is the one classifier, read after every core call (#60, #65). Every body is read through `ApiJson` and every query through `ApiQuery`, whose rejections are 400 `invalid_input` with axum's text, and the router's two fallbacks give an unknown path a 404 and a wrong method a 405 with a body, so every error but the timeout's 408 carries `kind`. `with_limits` composes `TimeoutLayer` from `[http] request_timeout_secs` on every route but `UNTIMED_ROUTES` (`/api/index`, `/api/init`) and `WRITE_ROUTES`, `DefaultBodyLimit` at `MAX_BODY_BYTES` and `GlobalConcurrencyLimitLayer` at `MAX_IN_FLIGHT`, one semaphore for the whole server. `WRITE_ROUTES` are the six write routes. API key authentication with `kn_` prefixed keys and read/write permission levels — a key generated before the rename keeps validating under its old `eg_` prefix. Per-key token bucket rate limiting (configurable requests/minute). CORS with configurable allowed origins for web-based agents. `--no-auth` mode for local development (127.0.0.1 only). Graceful shutdown via `CancellationToken` coordinating MCP + HTTP + watcher exit. `ApiState` holds a `Core` beside the HTTP-only fields (keys, rate limiter, `no_auth`), and its read handlers use `with_reader` and `with_core` while its write handlers use `core_within`.
- `openapi.rs` — the OpenAPI 3.1 document for the HTTP surface, generated at `GET /openapi.json` and never written by hand. One `rmcp::schemars` generator runs over every capability's `params` struct through `JsonSchema::json_schema`, the same derive an MCP client is shown, with `definitions_path` at `/components/schemas` so nested types (`Edit`, `EditContent`, `EditMode`, `Include`, `Sort`, `Scan`, `DeleteMode`, `GroupBy`) are hoisted there; `params_schema` is the one match from a capability name to its struct, and `every_operations_parameters_are_the_mcp_tools_properties` holds it to the tool list, which registers the same structs through `serve.rs`. What a struct cannot say comes from `surface::OPERATIONS`: the `operationId`, a summary a test caps at 300 characters because ChatGPT's importer refuses more (#87), and the 200 reply's prose. `query_parameters` is the GET rule, written once: an `array` property is one comma-separated `string`, since `serde_urlencoded` reads no sequence (#61), and the `null` schemars adds for an `Option` is dropped, since an absent parameter is the null. A POST body is the struct schema as emitted. `components.schemas.Error` is `{error, kind}` with `kind` an enum over `Fault::KINDS` and `ApiError::TRANSPORT_KINDS`; `components.responses` has one entry per status, and every capability operation references all seven, with a test tying each kind to the status `From<anyhow::Error> for ApiError` answers. `info.version` is the crate's. `/api/health-check` is the transport's own operation with `security: []`. `[http] public_url` is the document's server URL when set
- `graph.rs` — vault graph agent. Extracts wikilinks (target *and* the `#Heading` it named, since #28), renders a line as a reader sees it (`render_wikilinks`, #118: an alias replaces its link and a plain link reads as its target, an embed is left alone because a reader of one sees the note it transcludes, and a `Cow` keeps a line with no link unallocated — `matching` compares it beside the raw line), resolves what a link names (`resolve_link_target`, moved here from the indexer in #99 because every reader of a link has to do it. It reads no alias, because Obsidian leaves `[[Sam]]` unresolved when only an alias matches; `Store::resolve_scope_links` tries the alias after it misses, so a `links_to` or `linked_from` name resolves by alias and an edge never does, #142), and enumerates the deep links a set of notes wrote (`deep_links_from`, #99: reads `chunks.text`, keeps the heading **as the source note wrote it**, which the edge table does not — an edge names a `to_chunk_seq` and a heading that no longer resolves is already flattened to `DOC_LEVEL`). One enumeration, two readers: a rename asks for the notes linking to it, `health` asks for every note and runs the graph lane as **personalized PageRank over the chunk graph** (`PprParams`, issue #29): the seeds are the restart distribution, mass accumulates by `sum` so co-citation counts, each source chunk's mass is divided by its weighted degree so hubs cannot re-elect themselves, and a `DOC_LEVEL` link divides across the passages it could mean. Expansion follows the links of the **seed's chunk**, not its whole file — `OFF_CHUNK_LINK_WEIGHT` (0.5) is what an edge keeps when some other passage of the same file owns it. The walk returns chunks, so the lane never has to guess which section it meant, and there is no admission filter: a chunk with little mass simply sorts last. `graph_expand` takes an optional tag scope and drops out-of-scope candidates after the mass sort and before `cap_per_file` and the `max_expansions` truncate, so a candidate that cannot be an answer does not spend a quota slot; the walk itself is untouched, so mass still flows through an untagged note to reach an in-scope one (#60)
- `profile.rs` — vault profile detection. Auto-detects PARA/Folders/Flat structure, vault type (Obsidian/Logseq/Plain), wikilinks, frontmatter, tags. Content-based role detection for people/daily/archive folders by content patterns (not just names). Writes/loads `vault.toml`
- `store/` — SQLite persistence, one `Store` over one connection, one file per table family: `mod.rs` (the struct, `open`/`open_memory`/`open_reader`, `init`, `transaction`, `meta`, `stats`, and the re-export of every public item, so `crate::store::X` is the path whichever file holds it), `schema.rs` (the versioned schema, `SCHEMA_VERSION`, the `STEPS` ladder and the frozen `migrate_to_1` and `migrate_to_2`), `files.rs`, `chunks.rs`, `vectors.rs` (the `chunks_vec` table and its width, and the step-2 copy of pre-vec0 BLOB vectors), `fts.rs` (the keyword index's declaration, triggers and queries), `edges.rs` (edges and unresolved links), `scope.rs` (`scope_clauses`, listings and scans), `tags.rs`, `properties.rs`, `aliases.rs`. Two declarations live outside `schema.rs`: `fts.rs` builds the keyword index from `[fts]` and reconciles it on every open; `vectors.rs` sizes the vector table to the model at index time and recreates it on open only when the store records a width and holds no table. **Transactions:** `Store::transaction(|store| ..)` is the one way to write transactionally — it begins `IMMEDIATE` when nothing is open and a savepoint when something is, commits or releases on `Ok` and rolls back on `Err`, so a nested call rolls back only its own writes; `run_index` wraps the walk in one and `index_file` nests inside it per file (#84). `conn()` is `#[cfg(test)]`. **Schema version:** `PRAGMA user_version` records which schema a store holds. A store at 0 — every store from before versions, and every fresh file — runs the probe-based `migrate_to_1` and is stamped 1; a store at the current version runs no step on open; one above it was written by a newer knapper and is refused as `StaleIndex`. `SCHEMA` and `migrate_to_1` are frozen: a schema change is `migrate_to_3` appended to `STEPS` with `SCHEMA_VERSION` bumped, and the array's length is the constant so one cannot move without the other. Step 2 drops the six inherited tables and copies pre-vec0 BLOB vectors into `chunks_vec`. Each step runs in its own transaction and stamps inside it. `foreign_keys`, WAL and `busy_timeout` are per-connection pragmas set in `init` on every open, not schema. Tables: `meta`, `files` (with docid, created_by, and `frontmatter`, the note's YAML block as written and with no `---` fences — nullable and with no default, because `''` is a note that carries none and NULL is a row written before the column existed, and reading the two alike would answer a confident count over a half-read vault, #137), `chunks` (with vector BLOBs, `text` — the whole chunk, which the reranker scores and the keyword index reads — `snippet`, the leading 200 characters for display and *derived from `text`* by `insert_chunk` so callers pass one string rather than two, `seq`, the chunk's ordinal within its file, and the two lexical columns of #37: `heading_path`, the breadcrumb `Note Title > H1 > H2 > H3`, and `tags_text`, the file's frontmatter tags sorted and space separated. `NewChunk` is the row as it is written, one argument rather than ten), `chunks_fts` (FTS5 **external content** over `chunks`, declared over `text` and whichever of `heading_path` / `tags_text` `[fts]` enables, kept in step by three triggers. It stores an index and no text of its own, so #11's bug class — the keyword index holding a different string from the chunk — is unreachable rather than fixed, and a delete SQLite performs itself on the cascade from `files` still reaches it), `edges` (vault graph, chunk-to-chunk: `(from_file, from_chunk_seq, to_file, to_chunk_seq, edge_type)` is the unique key, with `DOC_LEVEL` = -1 for an end that names no passage — a sentinel rather than NULL because SQLite counts two NULLs as distinct in a UNIQUE constraint and `INSERT OR IGNORE` would stop deduplicating. Only the fine grain is stored; the document view is `wikilink_pairs()`, a `SELECT DISTINCT`), `unresolved_links` (the wikilink targets that resolved to no file, keyed on `files(id)`), `tags` + `file_tags` (a tag is an attribute of a note, so the junction is the fact and every count over it is derived: usage is `COUNT(*)`, and last use is `MAX(files.mtime)` over the tag's files, which is when the vault last wrote it. `tags.path` is folded and unique, so `Type/Undead` and `type/undead` are one row and one axis value, and the first spelling indexed supplies `display`. The schema stores no `parent_id` and no `depth` — a leaf row has no parent to orphan, so deletion has one rule and no recursion. `reconcile_file_tags` owns one file's rows the way `index_file` owns its chunks: read the ids the file holds, replace them, then delete each released id that no other file holds. The store folds the path it is given, so the identity column is folded whatever a caller passes), `properties` (one row per custom-property value, `(file_id, chunk_seq, name, value, kind, target_file)`; a frontmatter row sits at `DOC_LEVEL`, a body row at its chunk; cascades off `files(id)`, and `target_file` is `SET NULL` because the property outlives the note it named; `replace_file_properties` owns one file's rows, `property_registry`/`property_values` are the vocabulary, `doc_properties_for_files` is the one query search hits read and `matched_properties_for_files` the one a property-filtered listing reads — it takes the term and the resolved `links_to` id, so the rows it answers are the rows `scope_clauses` selected on — and nothing on the query path reads the table — #66), `aliases` (one row per alias a note's frontmatter lists, `(file_id, folded, display)`, unique on `(file_id, folded)` and indexed on `folded`; one table and not a vocabulary table beside a junction, because an alias names one note and an alias two notes carry is the case a lookup refuses; cascades off `files(id)`; `replace_file_aliases` owns one file's rows, `find_file_by_alias` is the read side's lookup — case-folded, on the whole alias, and an alias more than one note carries is an error naming every candidate — and `aliases_for_files` answers a listing's rows in the note's own order — #142). `list_files` takes a `tags::Scope` — every `all` term, at least one `any` term, none of the `none` terms — ANDed with `created_by`, and answers `ORDER BY f.path`, which the UNIQUE index on `files.path` serves with no sort step. Its `limit` is an `Option`: absent emits no `LIMIT` clause; `list_files_with_links_in` takes `after` beside it, a keyset condition on `f.path` in path order and on `(links_in, path)` through a subselect under a ranking, since `links_in` is a result column (#143); a caller's directory filter is a scope term, a case-sensitive range and never a `LIKE` (#65, #68); `tags_under` answers the vocabulary, whole or under one term folded to its subtree reading, as `TagCount { path, display, note_count }` ordered by path; `files_in_scope` answers the file ids the same `Scope` admits; `for_each_scan_row_in_scope` streams every row a `Scope` admits past a visitor — the note's frontmatter and its chunks, as one `UNION ALL` rather than two passes, the frontmatter arm sitting at `DOC_LEVEL` so -1 sorts it before chunk 0 and a note's YAML leads its own prose, which is what keeps `limit` cutting in vault order; `params::Scan` selects the arms. It is what `matching` reads (#106, #137). `frontmatter_unindexed` answers whether any note in scope predates the column, per-scope rather than per-store so a scope of freshly indexed notes answers while the rest of the vault waits; `set_file_frontmatter` is the write, called by the edge pass; and the private `scope_clauses` builds those clauses for all of them — a junction `EXISTS` for a tag term, a `files.path` range for a directory term — so a scope and a listing cannot drift apart (#60, #65). Both constructors — `Store::open` and `Store::open_memory` — register rusqlite's `rarray` module, which is how a resolved scope binds to a lane query as one pointer rather than one parameter per id. `chunks_vec` virtual table (sqlite-vec) for KNN search, declared at the embedding model's own width — it is not created until something establishes that width, since `Store::init` runs before any model loads. `ensure_embedding_dim()` sizes it at index time and discards the index if the width changed; `verify_embedding_dim()` guards the read and write paths. `fts_objects_sql()` builds the keyword index's declaration and its triggers from `[fts]`, and `fingerprint`'s `fts_fingerprint` hashes that text, so the enabled columns reach the fingerprint through the declaration itself; `rebuild_fts()` drops the table and its triggers, redeclares them and re-derives the index from the `chunks` table with no vault read and no model, which is the action that mismatch declares. `ensure_fts_table()` runs at init, where no config has been read, and leaves an index it did not declare alone; `sync_fts_objects()` is how a write path reconciles the declaration with `[fts]`. Enhanced `resolve_file()` with fuzzy Levenshtein matching as final fallback. It reads no alias: `update`, `move`, `archive` and `delete` resolve through it, and a destructive call reached through a name the caller did not know was an alias fails worse than `File not found` (#142)
- `prefix.rs` — what a chunk is embedded as, both fields. `DocContext::from_file` parses a document's identity (path, stem, frontmatter `name`, aliases, tags — the breadcrumb leads with the **path** since #46, because `name` is a cc-isekai convention knapper reads and never writes and Obsidian titles a note by its filename; `[breadcrumb_root]` selects `path` / `name` / `stem`, it is a chunker-digest component because it is stored in `chunks.heading_path`, and `name` reproduces the pre-#46 binary exactly); `embed_inputs` composes each chunk's `title:` field and its body, and is the one composition the indexer and the write pipeline share — `EmbedComposition` carries the two settings together so a caller cannot thread one and forget the other, which would write vectors into a space it does not share. The body carries the contextual prefix when `[embedding_prefix]` is on (#2); the title carries the note name or the breadcrumb (#36). Storage, snippets and the keyword index keep the raw chunk body, so the prefix cannot leak into results. `breadcrumb()` is the one composition of design §5.4's rule, and `lexical_fields` is its other limb: the same string, stored on the chunk row for the keyword index to match rather than averaged into a vector (#37). `PrefixConfig` is off by default and each component (`path`/`heading`/`tags`/`aliases`) is separately switchable — see `eval/probes.md` for why.
- `fingerprint.rs` — what built the index, so the store can tell when that changed (#31). Six `meta` keys — `parser_`, `chunker_`, `link_`, `fts_`, `embedding_`, `reranker_fingerprint` — each with one declared `Action` on mismatch: `Reindex`, `RebuildEdges`, `RebuildFts`, or `InvalidateThresholds`. Two kinds of input: *data*, hashed exactly (chunk limits, the text `store::fts_objects_sql` builds from `[fts]`, config, model and tokenizer artifact digests), and *algorithm*, carried by a hand-bumped version constant because there is no runtime view of what a function does. `CHUNK_RECORD_VERSION` sits beside `CHUNKER_VERSION` in the chunker's digest and asks the other question: not whether the chunks would fall in the same places, but whether the row written for a chunk still holds what a reader needs. `artifact_digest` hashes a model's **bytes** — a filename is not identity — and caches the result in a `<model>.sha256` sidecar keyed on `(size, mtime)`, so the steady-state cost is a `stat` rather than 640 MB of SHA-256. `verify()` is the read-path guard and it *refuses*, matching `verify_embedding_dim`; `record()` runs at the end of an index, never alongside it, so a crash cannot leave a store claiming to match code that never finished. A store with no rows adopts every key it is missing, since nothing indexed cannot be stale; a store that *holds* rows adopts only a key whose action is `InvalidateThresholds`, and reports any other absence as a mismatch, because absent and different have the same consequence for the rows on disk (#141). `Mismatch::stored` is `None` where the key was never recorded, which is what the refusal and the index-path line say out loud
- `indexer.rs` — orchestrates vault walking (via `ignore` crate for `.gitignore` support), diffing, chunking, embedding, writes to store + sqlite-vec + FTS5, and vault graph edge building (wikilinks). `run_index` reports through an `IndexProgress` sink and draws nothing; `main.rs` draws the bar, and `run_index_shared` reports nothing. Exposes `index_file`, `remove_file`, `rename_file` as public per-file functions. `reindex_written_file` takes the caller's `Config`; nothing on a server path reads `config.toml` again. `run_index_shared` accepts external store/embedder for watcher FullRescan. Reconciles the store's embedding width against the model before writing anything, forcing a full rebuild when it changed, then reconciles the six fingerprints (#31) and applies whatever they declare — and an `embedding_fingerprint` mismatch also prints that `[calibrated]` is fit to the embedder that is going away, gated on `Config::calibration_needs_refit`, because the re-index the fingerprint declares is not what is missing (#103) — a full rebuild, `rebuild_fts`, or `rebuild_all_edges`, which re-derives every edge from the *vault* rather than from `chunks.text` because the chunker strips frontmatter and a chunks-only rebuild would silently drop the links written there. Fingerprints are recorded last, on the way out. `index_file` reconciles the file's tag rows from `tags::extract` as its last step, and `remove_file` reads the ids the file releases before the cascade and prunes them after it. `build_edges_for_file` also records the file's YAML block in `files.frontmatter` (#137) — it is the pass that already splits the text to derive the properties, so the block and the rows read out of it describe one revision of the note. The same pass writes the note's `aliases` rows from `aliases::extract` over that block, under the same `ContentSource::File` rule (#142). It takes a `ContentSource` for that reason: `backfill_edges_from_chunks` hands it chunk text, which is the note with its block already stripped, and writing that would record "this note has no frontmatter" over a note that has one. `reconcile_links` and `sources_linking_to` are the cross-file half of the link graph (#108): what `build_edges_for_file` writes for one note is a claim about a *second* note, and a change to that second note is invisible to the first note's content hash. `remove_file` and `rename_file` take `vault_path` for that reason — they repair the notes that link to the file before they return. The write pipeline calls the same reconciler at the six places it used to author `files.tags`, so the vocabulary has one author.
- `temporal.rs` — temporal search lane. Extracts note dates from frontmatter `date:` field or `YYYY-MM-DD` filename patterns. Heuristic date parsing for natural language ("today", "yesterday", "last week", "this month", "recent", month names, ISO dates, date ranges). Smooth decay scoring for files near but outside target date range. Provides `extract_note_date()` for indexing and `score_temporal()` + `parse_date_range_heuristic()` for search
- `search.rs` — hybrid search orchestrator. `search_with_intelligence()` runs the full pipeline: retrieval for the user's query and no other (semantic + FTS5, then the graph lane off the merged seeds) → the ranking stage in `ranking.rs`, which by default fuses the two content lanes, routes graph and temporal candidates into the shortlist by reserved quota, and lets the cross-encoder sort it (issue #30). With no cross-encoder configured the sorted stage still runs and a calibrated logistic sorts the pool instead: each content lane's score normalizes onto one absolute `[0, 1]` scale and `apply_calibrated_scores` fuses the pair with three fitted coefficients into the same `rerank_score` slot the cross-encoder writes, so the sort, the floor and the confidence all read one field (spec 2026-08-30). `[calibrated] enabled = false` routes a no-model build to the legacy stage instead, byte for byte — the control. `[ranking] mode = "legacy"` restores the pre-#30 five-lane RRF, with the cross-encoder as a fourth voter and a per-file cap on the *results*. Both stages converge on `finalize_search_output`, which applies `coalesce::coalesce_adjacent` there, so the merge runs whether or not the cross-encoder ran (#39). It is also where `top_n` is honoured: `admit_for_top_n` builds candidates in rank order until `coalesce::blocks` counts `top_n` of them, because cutting the candidates at `top_n` and merging afterwards returned `top_n` minus however many merges fired — a shortfall that moved with the data, so no value returned a known number of results (#102). The candidates are the pool the answer floor already filtered, so the top-up admits no row that was not an answer, and `[ranking] candidates` is the ceiling no `top_n` reaches past. Admitting a candidate can also lower the count, when it is the section that gathers rows already admitted; the scan stops at the first prefix that reaches `top_n`, so it takes the fewest candidates that answer the request. A `Presentation` carries the store, the rerank window, `top_n`, the merge flag and the stage's own score function, so the two call sites hand one value to one path. `SearchConfig::scope` is the `Scope` a query runs under — tag terms, directory terms, or a mix in the same `all`/`any`/`none` — empty by default: `search_with_intelligence` resolves it once through `Store::files_in_scope` **before it embeds anything**, hands the ids to all three retrieval lanes and to `temporal_seeds`, and short-circuits to an empty result — no model call, no lane — when the scope admits no note. Resolving first is what separates the two failures a scope has: a term naming no tag or directory at all errors out of `files_in_scope` with the nearest one, while a scope no note satisfies is answered honestly and empty (#60, #65). Each lane keeps **two pools**: the lane's own scores feed fusion (which reads rank), while a min-max copy normalised into `[0.1, 1.0]` per lane feeds `merge_seeds` and the graph lane (which reads magnitude) — `1.0 - distance` and negated BM25 do not share a scale, and normalising the *fusion* pool instead measurably regressed the probes (issue #26). Lanes dedup on `(file_id, chunk_seq)` and cap each document's share (`max_chunks_per_file` under the legacy stage, defaulting to 3; `[ranking] shortlist_cap` under the sorted one, defaulting to 8). The sorted stage caps the **shortlist** and not the results — bound what the model is shown, because it cannot rank what it never saw; do not bound what it returns, because ranking is its job. `group_by = "file"` still collapses to one result per document under both. Lane weights come from `[lane_weights]`; the temporal lane's date range comes from `temporal::parse_date_range_heuristic`, a regex over the query. Results display normalized confidence percentages (0-100%) instead of raw RRF scores. `--explain` prints the retrieval step as well as the fusion step: the query as run, its FTS MATCH expression, per-lane hit counts, and — under a scope — a `scope: all=type/ -> 3 notes` line carrying the filter as the caller wrote it and the number of notes it resolved to, which is the first thing that explains a thin scoped result (#60). Under the calibrated sort, `--explain` also prints the query's BM25 bound and per-term idfs beside the MATCH expression, with each candidate's probability shown as the `calibrated` lane contribution. `rerank_documents()` fetches each candidate's whole chunk, truncates it to `[rerank] max_document_chars` if one is set — it is 0, unlimited, by default since #42 — before prepending any title, so the title cannot be what gets cut, and logs the assembled size at DEBUG — `RUST_LOG=knapper::search=debug` is how `eval/sweep-rerank-chars.py` reads the character counts back.
- `packaging.rs` — the output contract (#35): the one `SearchEnvelope` every surface renders. `assemble` fills `blocks` greedily against `budget_tokens` and turns the rest into `overflow`, text-less `Summary` rows naming what did not fit — the included set is a prefix, so the fill stops at the first result that would break the budget and never skips past it. `full` ignores the budget and `summaries` returns every rank as a summary, which is the one overflow the budget did not cause. `warnings` carries the reason the budget shortened an answer, and `render_text` prints it above the excluded list, because "lower relevance" is the rank order and not why those rows were cut (#102). `notes` is the frontmatter properties of each note the included blocks came from, keyed by path and held once however many of that note's sections answered, because a note that answers with four of its sections would otherwise carry four identical copies (#119). It is omitted when no answering note carries a property, so a vault with no custom properties renders as it did before (#66). `PropertyValue` is one row under its kind's own JSON type — `store::PropertyRow` carries every value as a `String` beside a separate `kind`, so the text alone cannot tell the number `5` from the text `"5"`, or a link from the words it is written with; a `link` keeps the note it resolves to in `path`, and a name the note carries more than once becomes a `List`, because a YAML list writes one row per element. The two row fields a search hit cannot vary are not carried: `doc_properties_for_files` selects `WHERE p.chunk_seq = DOC_LEVEL`, so `chunk_seq` is always the sentinel and `heading_path` is always absent. `Provenance` is what the machine channels report in place of a number, derived from the fused lane contributions; `Provenance::lanes` is what the wire carries — the lanes that fired, named the way `render_text` names them, where three booleans and an empty `linked_from` cost a caller more than they say. `linked_from` reaches no surface until the graph lane attributes its seeds (#74), and stays on `Provenance` so `coalesce` still merges it; `est_tokens_fallback` is the `ceil(chars / 3.33)` estimate for a result with no scored window to read a count from
- `onboarding.rs` — the two `init` flows, both JSON: `run_detect_json` reads the vault's type, structure and stats and writes nothing; `run_apply_json` writes `vault.toml` and runs the index through the caller's config and progress sink. `init` takes `mode: detect | apply` on every surface (#62)
- `cli.rs` — the clap command tree, one variant per capability. A variant's arguments come from its `params` struct, so the command line, the MCP schema and the HTTP route read one declaration; a variant carries a field of its own only where the CLI has an argument the other surfaces cannot have, and `surface::CAPABILITIES` names each of those with its reason (#62)
- `pipe.rs` — what the CLI does when the reader of its output goes away (#128). Rust sets `SIGPIPE` to `SIG_IGN` before `main`, so a write to a closed pipe returns `EPIPE` and `println!` panics on it; `restore_default_sigpipe` puts the default disposition back before any output, `--help` included, so `knapper tags | head -3` ends quietly
- `exclude.rs` — exclude-pattern matching for vault ingestion. `config.exclude` is documented as glob patterns and `ExcludeMatcher` is what makes that true: `.gitignore` conventions, where a separator decides whether a pattern is anchored to the vault root or matches at any depth; `walk_vault` and the watcher both match through it, so the indexer and the watcher cannot drift apart
- `params.rs` — what each capability takes, declared once. One struct per capability, deriving `clap::Args` for the CLI, `Deserialize` for MCP and HTTP, and `JsonSchema` for what an MCP client is shown. Because the three come from one declaration, a parameter cannot be named differently on two surfaces or exist on one and not another. Container encoding still differs where a surface forces it: a GET route reads `?all=a,b` as one comma-separated value, because `serde_urlencoded` reads no sequence (#61). `Edit` carries `heading`, the new heading text of the section it renames (#97), and `after`/`before`, where a property key the note does not carry is written (#113). `scope` is the alias of `all` on `Search` and `List`, and every one of the four fields carries tag terms and directory terms alike — a leading `/` reads a field's term as a directory path instead, a trailing `/` its subtree (#65). `List` declares `detailed`, so the outline is one field on all three surfaces; its `limit` is an `Option<usize>` whose absent case is no limit (#68), and `after` is the path a page starts after (#143).
- `surface.rs` — the table of what every capability is called on each surface, and the tests that hold the three surfaces to it (#62). One transform gets from any spelling to any other: CLI kebab-case, MCP with `-` written as `_`, HTTP under `/api/` and the kebab name. Three parity tests compare the table with what `cli::Cli::command()`, `KnapperServer::tool_router()` and `http::routes()` register, so a call added to one surface and forgotten on another fails the build. `OPERATIONS` is one row per capability — `operationId`, summary, 200 description — that `openapi.rs` reads beside the struct schema; tests hold it to one row per HTTP capability, unique ids and the 300-character summary cap. `render_table` generates `surfaces.md`, and a test fails when the committed file is stale

`cli.rs` declares the command tree and `main.rs` dispatches it (async via `#[tokio::main]`). The tree lives in the library so that `surface.rs`'s parity test can walk it under `cargo test --lib` (#62). Every capability is one top-level command: `index` (with progress bar), `match` (a literal string over a note's prose and its frontmatter both, with the same four scope operators, `--case-sensitive`, `--scan body|frontmatter|all` narrowing which half is read (#137), and `--limit`, whose absent case is every matched line and whose `0` is none — the note and line counts are whole whatever it says, because the count is the answer to the absence question (#106)), `search` (with `--explain`, loads intelligence models when enabled, and `--scope`/`--all`/`--any`/`--none` — the four scope operators `list` takes, tag or directory terms alike, scoping the query to the notes they admit (#60, #65), and `-n/--top-n`, which defaults to `top_n` in `config.toml` on all three surfaces), `read` (a note's content, or one of its sections with `--section`, the body alone with the heading named beside it (#96); the output is one bare path per line, so `wc -l` is the total, and `--detailed` puts each note's heading outline under its path, an ATX heading as its `#` markers and a promoted bold line in its bold form), `tags` (the vocabulary, whole or under one term with `--under`), `vault-map`, `create`, `update` (one edit as `--section`/`--property` + `--mode` + `--content`, with `--heading` renaming the section `--section` names and `--after`/`--before` placing a property key the note does not carry, or the whole grammar as a JSON `--edits` list), `delete` (`--mode soft|hard`), `move` (`--new-folder`), `archive` (`--undo` restores), `reindex-file`, `status` (index statistics, intelligence state, date coverage, and the edge and wikilink counts), `health`, `init` (`--mode detect|apply`), and the four that configure the process rather than the vault: `configure` (`--enable-intelligence`, `--disable-intelligence`, `--model`, `--add-api-key`, `--list-api-keys`, `--revoke-api-key`, and `--setup-chatgpt`, which enables HTTP, mints a read key when there is none and allows the two ChatGPT origins, with no prompt), `models`, `clear`, `serve` (MCP stdio server with file watcher + intelligence + optional `--http`/`--port`/`--host`/`--no-auth` for HTTP REST API).

## Key patterns

- **The keyword lane reads the chunk table:** `chunks_fts` is an FTS5 **external-content** table over `chunks`, declared over `text` plus whichever of `heading_path` / `tags_text` `[fts]` enables, and kept in step by three sync triggers (#37). It stores an index and no text of its own, so #11's bug class — the keyword index holding a different string from the chunk — is unreachable rather than fixed, and the triggers are the only writer: a chunk row inserted, updated or deleted by any path updates the index, including the delete SQLite performs itself when `files` cascades. `'rebuild'` reproduces the trigger-built index's postings and BM25 scores exactly; the *bytes* differ, because an incremental write leaves one segment per batch where a rebuild writes a single merged one
- **5-lane hybrid search:** Queries run through up to five lanes — semantic (sqlite-vec KNN embeddings), keyword (FTS5 BM25), graph (wikilink expansion), cross-encoder reranking, and temporal (date-range scoring). Lane weights come from `[lane_weights]` and default to the vector the #57 pool cells measured; the graph lane is held at or below the content lanes (issue #9), a weighting set when graph expansion excluded the seed files and so could never accumulate RRF agreement. It no longer excludes them (#29), and the weights have not been revisited since. Under the default sorted stage the two content lanes are fused by RRF into a shortlist, the graph and temporal lanes fill their reserves in it, and one absolute scorer sorts what results: the cross-encoder when one is configured, otherwise the calibrated logistic over normalized cosine and BM25 (spec 2026-08-30). `mode = "legacy"` is the five-lane RRF control, the cross-encoder among the voters. The temporal lane activates on a date range parsed from the query by regex
- **Vault graph:** `edges` table stores directional wikilink edges (one per `[[link]]`; the reverse edge exists only when the target links back). Built during indexing after all files are written. An edge is **owned by its source file's content**: only that file's re-index may create or destroy it, which is why the re-index path calls `delete_outgoing_edges_for_file` and only file *removal* calls `delete_edges_for_file` (both directions). Both `edges` columns CASCADE off `files(id)`, so re-indexing must not delete the row either — see `index_file` step 5. Wikilinks that resolve to no file are recorded in `unresolved_links`, keyed on `files(id)` and CASCADEing off it the way `chunks`, `edges` and `file_tags` do — a source **path** made it the one per-file table `DELETE FROM files` could not reach, so six removal paths each owed a manual cleanup and one paid it (#98). Both rows are claims about a second file, so **a note that appears, goes or moves invalidates the links other notes wrote**: `indexer::reconcile_links` re-derives the notes a change could have altered, from the `unresolved_links` rows the vault can now satisfy and from `sources_linking_to`, read before a removal takes the edges with it. Every path that inserts, removes or re-paths a `files` row calls it — the walk, `verify_index_integrity`, `reindex_written_file`, the watcher, `create`, `delete`, `archive`, `unarchive` and `move` (#108).
- **Graph agent:** One PPR iteration out of the seed chunks, following wikilinks in either direction — outgoing links and backlinks (`Store::incident_wikilink_edges` returns both, oriented near-end-first, in one indexed fetch for the whole frontier). `α` damps each iteration and is inert at one. The lane does not read the query at all: its old admission filter was a weaker second copy of the FTS lane, scoped to one file. Output is capped per document at whichever lane cap the stage selected — `[ranking] shortlist_cap` under the sorted stage, `max_chunks_per_file` under legacy — and truncated to 20, both cuts on accumulated mass
- **Edge granularity:** an edge's source is the chunk whose text held the link, so `build_edges_for_file` reads the file's chunks from the store and **requires them to be inserted already**. A link the chunker never sees (frontmatter) is attributed to `DOC_LEVEL`, which is why it still takes `content`. Target side: `[[Note#Heading]]` resolves to the chunks under that heading, and a plain link — or a heading that has since been renamed — becomes `DOC_LEVEL` rather than nothing. `indexer::backfill_edges_from_chunks` re-derives the whole table from `chunks.text` with no vault read, which is how a pre-#28 store adopts the grain; `Store::needs_edge_backfill` is the flag the migration raises
- **Incremental indexing:** `diff_vault()` compares file content hashes in SQLite against disk. A changed file keeps its `files` row — and therefore its id, and therefore every backlink keyed on that id — while its chunks, vectors, FTS rows and *outgoing* edges are cleared and recomputed; `insert_file` upserts on `path`. `writer::move_note` and `delete_note`'s soft mode likewise move the row with `update_file_path` rather than replacing it — a relocation is not a deletion, and replacing the row cascades the note's chunks, vectors, keyword rows and edges away with nothing to put them back (#27, and the soft-delete path until #98). `an_incremental_edit_and_a_full_index_agree_on_the_edges_table` (`indexer.rs`) is the invariant. Content hashes are blind to everything *outside* the file, which is what `fingerprint` covers: a chunker constant, the embedding prompt, the link resolver or the FTS schema can all change with no file changing, and `run_index_inner` reconciles those before it diffs anything
- **sqlite-vec for vector search:** Vectors stored in a `chunks_vec` virtual table (vec0). KNN search via `vec_distance_cosine()`
- **Write pipeline:** four steps for creating a note: (1) resolve tags via fuzzy matching against the tag store, (2) discover potential wikilinks via exact + fuzzy matching, (3) atomic file write (temp + rename for crash safety), (4) immediate index update (embed + insert into sqlite-vec + FTS5 + edges)
- **Warm sync (file watcher):** OS thread watches vault via `notify-debouncer-full` (2s debounce), on a backend chosen by `[watcher].backend` — native inotify/FSEvents, or a `PollWatcher` fallback for bind-mount/overlay/network filesystems inotify cannot service, auto-detected via `statfs` (#83). Events sent over `tokio::mpsc` to async consumer. Two-pass processing: mutations then edge rebuild. Move detection via content hash matching. Startup reconciliation diffs the vault and queues the changes as per-file events
- **Fuzzy link matching:** Sliding window of N words over content, compared via `strsim::normalized_levenshtein` with 0.92 threshold. First-name matching for People notes (uniqueness check, 650bp confidence, suggestion-only). Overlap resolution: exact > alias > fuzzy > first-name
- **Docids:** Each file gets a deterministic 6-char hex ID. Displayed in search results
- **Vault profiles:** `knapper init` auto-detects vault structure and writes `vault.toml`
- **Two absolute scorers:** the sorted stage sorts the shortlist by a probability, and which scorer produced it depends on what is configured. Qwen3-Reranker-0.6B scores query-document relevance via Yes/No logit softmax over the top-32 candidates, reading each candidate's whole `chunks.text` rather than a lane-dependent preview — which is why it is roughly half the cost of a reranked query (`eval/probes.md`, #14); under `mode = "legacy"` it is a 4th RRF voter instead. With no cross-encoder configured — the default install — the calibrated logistic scores the same slot with no model call, from each candidate's cosine and its BM25 against the query's own upper bound (spec 2026-08-30). Each scorer carries its own floor, because each was fit against its own scores
- **llama.cpp backend:** Global `LlamaBackend` singleton via `OnceLock`. `LlamaModel` is `Send+Sync`, `LlamaContext` is `!Send` (created per-call). Metal GPU auto-detected on macOS. Models download from HuggingFace on first use with progress bar. Every context sets `n_threads` + `n_threads_batch` from `resolve_n_threads`, which defaults to **physical cores** — llama.cpp's library default is a flat `GGML_DEFAULT_N_THREADS = 4` on any machine, and counting logical CPUs instead is measurably *worse* than that on an SMT box (issue #20)
- **Prompt formatting:** `PromptFormat` auto-detects model family from GGUF filename and applies asymmetric prefixes in `embed_query` (queries) and `embed_batch` (documents). The family decides three things and not one (#8): the templates, which forward pass runs the graph, and which special tokens llama.cpp adds — see `llm.rs` above. Qwen3-Embedding's query is the model card's `Instruct: {task}\nQuery:{query}` and its document is the bare text, because the card gives the instruct to the query half alone and there is no `title:` field to fill; `eval/smoke-qwen-embed.sh` is what proves the EOS reaches the model, by indexing one note twice — once with a literal `<|endoftext|>` — and reading the cosine between the two stored vectors, which moves 0.84 to 0.996 across the fix. The `EmbeddingGemma` pair is the one its model card documents — `<bos>task: {task} | query: …` and `<bos>title: {title | none} | text: …` — and each half is selectable, `[embedding_prompt] document` / `query`, with `legacy` restoring nomic-embed-text's `search_query:` / `search_document:` convention as the control (issue #10). The `<bos>` is in the template because `str_to_token` is called with `AddBos::Never`. The `title:` field holds whatever `[embedding_prompt] document_title` names, composed per chunk by `prefix::embed_inputs` (issue #36). Which document template built a store is hashed into `embedding_fingerprint` from `PromptFormat::template_id`, and the title selection is hashed beside it, so switching either re-indexes; the query half reaches no fingerprint.

## Data directory

`~/.knapper/` by default, resolved by `Config::data_dir()` through `config::resolve_data_dir`: the `--data-dir` override (a `OnceLock` set once in `main` before any read) wins, then `KNAPPER_HOME` (used verbatim, empty reads as unset), then `~/.knapper`. Everything derives from it, so one override moves them together (#77). Contains the store (SQLite with FTS5 + sqlite-vec + edges), `models/` (GGUF models + tokenizers), `vault.toml` (vault profile), `config.toml` (user config with intelligence toggle + model overrides). `config::db_path()` resolves the store file: `knapper.db` for a fresh directory, with a read fallback to a legacy `engraph.db` left by a store from before the rename.

Single vault only. Re-indexing a different vault path triggers a confirmation prompt.

Carries the 2026-07-28 lifecycle as well as the handshake before it (#109); 3.5 is the floor, because 3.2 bound a session that opened with `server/discover` to per-request `_meta`, so a client that fell back to `initialize` had its `tools/list` refused

## Testing

- Unit tests in each module (`cargo test --lib`) — 1481 tests, no network required. `MockLlm` stands in for the embedder and the cross-encoder, so the write, index and search paths all run with no model download. There is no `tests/` directory: a test that reaches the shipped code through the same public API the module tests use belongs beside them, and the two `#[ignore]`d files that used to live there asserted against a copy of the v0.6 pipeline
- End to end, against a real binary: `eval/smoke-tags.sh <scratch-home>` drives the CLI, the MCP stdio handshake and the HTTP endpoint against a store seeded without a model, after one `knapper index` over an empty vault records its fingerprints, and `eval/smoke-match.sh <scratch-home>` does the same for `match`, asserting that the three surfaces answer one report and that a pattern no note holds answers `notes: 0`. `eval/smoke-properties.sh <scratch-home>` does the same for `properties`, against a small vault it indexes for real, because the rows come from the edge pass. `eval/smoke-qwen-embed.sh` is the one that needs the Qwen3 model — it downloads Qwen3-Embedding-0.6B (639 MB, once; `KNAPPER_MODEL_CACHE` reuses a warm one) and checks the store came out 1024 wide, that a query resolves, and that the model's trailing EOS is being appended. It uses `target/release/knapper` without building it, so build first or a stale binary answers
- Build requires CMake (for llama.cpp C++ compilation)

## CI/CD

- CI: `cargo fmt --check` + `cargo clippy -- -D warnings` + `cargo test --lib` on macOS + Ubuntu. Ubuntu step installs CMake. **Manual dispatch only in this fork** (`gh workflow run ci.yml`) — it does not run on push or PR, so those three commands are the local gate before every commit.
- Remotes: `origin` is `mightytribble/knapper-private`, `public` is `mightytribble/knapper`, `upstream` is the pre-fork `devwhodevs/engraph`. Releases are published on **public**, so `main` and the tag go to both remotes and the workflow is dispatched against public.
- Release: native builds on macOS arm64 (macos-14) + Linux x86_64 (ubuntu-latest). Manual dispatch only (`gh workflow run release.yml --repo mightytribble/knapper -f tag=v0.9.x`); it does not fire on tag pushes. Bump `Cargo.toml` and add a `CHANGELOG.md` entry in the same commit as the tag.
- Homebrew: `mightytribble/homebrew-tap` — formula builds from source tarball. Depends on `cmake` + `rust`. The `update-homebrew` job **regenerates the whole formula** from a heredoc in `release.yml`, so an edit made in the tap by hand is overwritten by the next release; change the heredoc, not the tap. It pushes with `HOMEBREW_TAP_TOKEN`, a fine-grained PAT held on the **public** repo with `Contents: write` on the tap alone. Without it the binaries still publish and only the formula goes stale, which is a quiet failure: `brew` keeps serving the previous version.
- `/docs/` and `/eval/` are gitignored — development measurement and design material, kept on disk and out of the repo. `CLAUDE.md`, `README.md` and the specs all reference files there that a clone does not contain, and nothing under either path should be forced into a commit.
